COURSE 04 · AGENT EVALUATION

真正的评测不是让模型选一个标签，而是让它把工作做完并留下可核验证据

Core 生成最小权限工作单，Agent Host 在隔离目录中执行不同变体；每个角色只看自己需要的上下文。最后返回的不是一句“成功”，而是 ExecutionBundle：产物、轨迹、错误、用量、时间和哈希。

预计 55 分钟角色隔离E0–E3 证据
01
CORE ↔ HOST

一次执行如何跨过 Core 与 Agent Host 边界？

Core / Planner冻结 case、variant 与权限，生成 WorkItem
Orchestrator领取工作，不拥有分数与候选状态
Executor Agent在隔离 workspace 真正完成任务
Submission返回 ExecutionBundle 和 artifact hashes
Core / Ledger校验、记账、缓存、恢复和后续分发
ExecutorWorkItem → ExecutionBundle（概念化）
# Core 发出的内容：只有完成任务所需信息
work_item = ExecutorWorkItem(
    case_id="loop-sparkles-006",
    variant="candidate",
    user_prompt="制作一个循环庆祝 GIF",
    fixture_refs=[...],
    skill_ref="candidate-package/",
    # 没有 assertions、rubric、sibling output
)

# Host 交回的不是自报分数，而是证据包
submission = ExecutionBundle(
    task_native_outputs=["celebration.gif", "delivery.md"],
    transcript_ref="transcript.jsonl",
    observed_trace_ref="trace.json",
    usage={"input_tokens": ..., "tool_calls": ...},
    timing={"wall_ms": ...},
    artifact_hashes={"celebration.gif": "sha256:..."},
    failure=None,
)
为什么要 artifact hash？

Grader 评分的必须是 Executor 当时生成的同一个文件。哈希把 WorkItem、产物与后续结论绑定，防止报告读取了后来被替换的文件。

02
PAIRED ISOLATION

为什么 no-skill、original、candidate 要“同轮但隔离”运行？

同一个 case

输入、环境、模型、scoring policy 尽量一致，差值更能归因于 Skill 版本。

相互不知道

每个变体有独立上下文与 workspace，避免读取兄弟输出后抄答案。

同一轮比较

减少环境版本、服务波动和任务难度差异造成的混淆。

paired_delta(case) = score(candidate, case) − score(reference, same case)

三个参考身份不要混淆

Variant读到的 Skill回答的问题
no-skill没有目标 Skill有 Skill 比 Agent 本身更好吗？
original未经优化的公开 Package候选比原始版本好吗？
candidate某个谱系节点的 Package这次 Patch 是否产生真实增益？
安全的运行时间优化

当环境、模型、EvalPlan、scoring policy 和输入哈希完全一致时，可复用 R3 封存的 no-skill/original 证据，只执行新 candidate。Executor、Grader、Analyzer 之间没有数据依赖的工作也可并行，但上下文仍隔离。

03
EVIDENCE TIERS

E0 / E1 / E2 / E3 不是四种总分，而是四种证据强度

它们解决“现在这份结论究竟建立在多真实的证据上”。

E0 · 静态文件、schema、语法、安全、依赖
E1 · 计划Agent 说明将如何做，不产真实业务产物
E2 · 执行实际工具调用、任务原生输出、trace
E3 · 断言在 E2 产物上运行确定性检查
综合判断Grader + Comparator + ScoreVector

E0 能证明什么？

Package 可解析、文件引用存在、脚本语法正确、没有已知安全违规。它不能证明 Agent 会正确使用这些资源。

E1 为什么保留？

它便宜，适合早期诊断、计划一致性和提出候选思路；但不再允许作为功能接纳证据，也不能把计划说得漂亮当作成功。

E2 是功能证据的地基

Agent 真正读取 Package、调用工具并输出 GIF、报告或代码等原生产物，同时记录 trace、错误与成本。

E3 必须依附 E2

例如读取真实 GIF 检查帧数和尺寸。框架不能凭空制造一个统一 result.json，再检查自己制造的字段。

断言通过率不是综合 Skill 质量

断言只能覆盖预先编码的条件；专业度、完整性、可用性和意外缺陷还需要独立 Grader 与匿名 Comparator。E3 可以是 1.0，TaskScoreVector 不应因此自动变成 1.0。

04
RUNNING CASE · ONE COMPLETE TIMELINE

同一个 GIF case 在评测系统里到底经历了什么？

T0 · Core 解析冻结计划

读取 loop-sparkles-006 的 prompt、fixture、variant matrix 和最低证据 E2；rubric/assertions 留在 grader 侧。

T1 · 三个 Executor 独立运行

no-skill 没有目标 Package，original 引用原始快照，candidate 引用某个 materialized child；三者 workspace 和上下文互不相见。

T2 · Host 回交 ExecutionBundle

每个变体返回真实 GIF、delivery 文档、transcript、observed trace、usage、timing、artifact hashes；timeout 或工具失败进入 typed failure。

T3 · E3 读取同一份 GIF

确定性 grader 根据 hash 定位产物，检查格式、画布、帧、时长和体积。它不自己生成替代业务文件。

T4 · 独立质量判断

Grader 按冻结 rubric 检查完整性与专业度；Comparator 获得匿名 A/B 输出并解释更偏好哪一个。

T5 · Core 形成 EvaluationRecord

核验角色 submission、证据引用和 provenance 后，把各结论变成下一章的 TaskScoreVector；角色不能自行更新 candidate pool。

输入状态FROZEN EVAL PLAN

计划 hash、环境/模型/策略 hash 已固定。

运行中状态DISPATCHED → SUBMITTED

ledger 支持中断、重试、缓存与恢复。

输出状态EVIDENCE VALIDATED

只有通过 schema、hash 和可见性检查的证据进入评分。

并行化边界来自依赖图，而不是“把所有角色一起跑”

三个 Executor 彼此独立，可并行；确定性检查和独立 Grader 要等各自 ExecutionBundle；Comparator 要等 A/B 都到齐；Analyzer 要等评分与 trace。只并行当前依赖已经满足的 work items，才不会破坏角色隔离和证据顺序。

05
INDEPENDENT ROLES

为什么一个 Agent 不能又执行、又评分、又改包？

角色可以看不可以看 / 不拥有输出
Executorprompt、fixture、自己的 skill_refrubric、兄弟输出、候选身份ExecutionBundle
Deterministic Grader真实产物、assertions不凭感觉改断言逐项检查证据
Independent Grader任务、rubric、产物、trace不负责提出 Patch质量评分与理由
Comparator匿名 A/B、关键要求真实 variant 身份胜/负/平 + 理由
Analyzer / ASI失败、trace、评分、图切片不直接接纳候选失败归因与修改范围建议

Executor 日志写着“GIF 完全满足循环要求”，Grader 应该怎样处理？

本章面试问答

E1 既不能验收，为什么不删除？
它适合低成本诊断和候选提案前的计划审查，可以减少明显无效的昂贵 E2。但证据层级必须写清，E1 不能越权成为功能结论。
默认 Agent-native 和 LLM API 是否冲突？
不冲突。默认由现有 Agent Host 承担各隔离角色，不要求额外 Key；可选 provider API 只是替换某个角色的执行后端，Core 契约、上下文隔离与 Gate 不变。
复用 baseline 证据会不会不公平？
只有环境、模型、EvalPlan、scoring policy、输入与相关哈希完全一致时才复用；引用关系写入 provenance。任何关键条件变化都必须重跑 paired reference。

本章结论

  • Executor 交付原生产物与 ExecutionBundle，不交自评答案。
  • paired variants 同条件、相互隔离，才能解释 Skill 增益。
  • E0–E3 是证据等级；E2 执行和 E3 断言互补。
  • 独立角色与最小上下文减少泄漏和自我偏见。

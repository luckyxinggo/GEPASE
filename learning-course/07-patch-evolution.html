COURSE 09 · PACKAGE PATCH

从“建议改一改”变成可定位、可校验、可回滚的 PackagePatch

Analyzer 给出失败假设，图选择器缩小范围，LLM 或 Agent proposer 生成 typed Patch。Applier 在隔离副本中检查前置条件并原子应用；任何一步失败都不会污染父候选。

建议学习 65–85 分钟7 类 Patch 操作SkillOpt 式有界编辑Darwin 式谱系历史
01
FROM FAILURE TO SCOPE

失败证据怎样变成修改范围？

Failure union合并多个 case 的失败节点
Reverse slice追溯上游影响节点
Selector ranking图、trace、风险与历史加权
Scope budget限制文件数和操作数
Patch proposaltyped ops + rationale
Affected closure决定验证与合并范围
关键边界

图负责提供“候选范围与风险信号”，Analyzer/Proposer 负责理解语义，Gate 负责验证效果。任何一个组件都不能单独宣称根因。

02
TYPED OPERATIONS

PackagePatch 有哪七类操作？

操作适用对象例子
replace_markdown_block某个 Markdown section重写“交付前验证”段，不覆盖整个 SKILL.md
insert_referenceMarkdown 引用把质量指南接入渐进披露入口
update_frontmattername / description / metadata修正触发范围
replace_python_function一个 Python 函数修复帧尺寸验证函数
replace_text_file小型纯文本文件更新配置模板
add_file新 reference/script/asset添加缺失的验证脚本
delete_file确认无依赖的冗余文件删除冲突旧指南；必须先检查 closure
一个有界 Markdown Patch（简化 JSON）
{
  "patch_id": "patch-verify-before-delivery",
  "parent_candidate_id": "original",
  "rationale": "3 个失败 case 未执行最终 GIF 检查",
  "operations": [{
    "op": "replace_markdown_block",
    "target_node_id": "SKILL.md#verification",
    "precondition": {"content_hash": "sha256:old..."},
    "replacement": "## Verification\n在交付前必须……"
  }],
  "scope_budget": {"max_files": 1, "max_ops": 1}
}
“有界”不等于只能改 SKILL.md

范围可以是一个函数、一个 reference 或一组 dependency closure 文件。关键是操作有类型、目标明确、数量受限，而不是把整个包交给模型自由重写。

03
FROM SKILLOPT + DARWIN TO PACKAGEPATCH

参考项目的修改思想怎样被推广到完整 Package？

思想来源原始直觉GEPASE 的推广额外风险控制
SkillOpt用 add/delete/replace 表达有界编辑操作带目标节点类型，可覆盖 Markdown、Python、reference、asset 和 metadataschema、precondition、scope budget、held-out strict improvement
SkillOpt拒绝未带来提升的编辑RejectedEditStore 记录 Patch、失败 Gate、回归 case family 与证据后续 selector 降权历史回归节点，仍允许有预算探索
Darwin skill执行→反思→修改→验证与版本历史每个 PackageCandidate 记录父代、Patch、snapshot、graph diff、evaluation 与 status角色隔离；反思器不拥有接纳权；Core 维护 DAG
GEPASE 扩展单文件编辑不足以表达调用关系affected closure 决定一起携带/检查的依赖，blast radius 决定验证强度禁止跨不同 Package merge，父快照保持不可变

为什么 typed operation 不是为了“格式漂亮”？ 因为 Core 需要在 LLM 提案之后继续做确定性工作：校验目标存在、检查类型兼容、验证旧 hash、估算依赖闭包、原子回滚和生成可解释 graph diff。

为什么保留自然语言 rationale？ 它为人类和下一轮 Reflection 提供语义理由；但 rationale 不能替代 operation，也不能替代评测。

为什么允许多文件 Patch？ 如果新增脚本却不更新 SKILL.md 引用，或修改配置却不携带消费它的代码，单文件编辑会制造残缺候选。因此范围“有界”与范围“只能一个文件”不是同一回事。

04
ATOMIC APPLY

为什么 Patch 必须先在隔离副本原子应用？

复制父快照父候选不可变
检查 precondition目标内容和 hash 未漂移
按序应用 ops任一步失败则整体失败
重建 IR/Graph检查新依赖和 diagnostics
生成 child snapshot新 hash、新 candidate ID

Precondition 防错位

父文件若已变化，旧 Patch 不能静默覆盖新内容。

Rollback 防半成品

第 3 个 operation 失败时，前两个也不会残留。

Graph diff 防暗伤

比较节点和边变化，计算 blast radius，决定后续 Gate。

这也是为什么项目不直接在用户原始 skills_test/ 或公开来源目录上改。所有候选都从只读输入快照物化到隔离候选目录。

05
RUNNING CASE · PATCH MATERIALIZATION

把 GIF 失败反思变成一个可重放 child

输入

父代 original、失败 case evidence、目标节点 SKILL.md#verification、允许 1 file/1 op 的 scope budget，以及该节点当前 hash。

提案

Proposer 把“交付前验证”改成顺序明确的硬约束：生成后检查 GIF 属性、必要时修复、再交付；不顺手重写无关 reference。

应用

Applier 克隆父快照，校验 precondition，替换一个 Markdown block，重建 IR/Graph；父代原目录和公开来源保持不变。

物化结果

产生新的 candidate ID、snapshot hash、changed node、graph diff、affected closure 和 Gate 0 输入；此时只是 materialized，还没有效果结论。

交给下一章 canary/Gate 的输出

child snapshot + PackagePatch + lineage + graph diff + train work items。只有真实 paired E2/E3、评分和 held-out Gate 能把它从“结构上可应用”推进为 deployable。

旧流程允许 improvement_or_equal 进入候选池，且基于 E1 proxy；现在完全等分不再视为接纳，功能候选必须连接新的 TaskScoreVector 与 held-out Gate。

本章面试问答

typed Patch 比 unified diff 好在哪里？
它知道目标节点类型、前置条件与操作语义，能做 schema 校验、影响分析和结构化回滚；unified diff 仍可作为展示，但不应是唯一契约。
怎样处理 Patch 改脚本后新增依赖？
重建 IR/Graph，检查 import/runtime requirement 与 dependency closure；Gate 1 验证环境和安全，受影响任务进入更强功能验证。
为什么保存 rejected edits？
失败同样是搜索信息。保存失败节点、Patch、Gate 与回归类别，可以降低重复提案概率，也让面试和报告能解释“哪些修改不值得保留”。

本章结论

  • 失败证据经图切片和 selector 变成有预算的 mutation scope。
  • PackagePatch 用七类操作表达跨文件有界修改。
  • 前置条件、原子应用、rollback 和 graph diff 保护父候选。
  • candidate status 与 rejected memory 让进化过程可追踪。

COURSE 03 · EVAL PLAN

优化器只会朝“考卷奖励的方向”进化，所以先把考卷设计对

旧系统最大的错误不是模型不够强，而是把异构真实任务压缩成 action classification，再由框架合成统一 result.json。新 EvalPlan 必须描述任务原生输出、内容期望、质量量表和可见性边界。

预计 50 分钟出题与审核流程避免 evaluator 漂移
01
TWO DIFFERENT QUESTIONS

Trigger Eval 与 Functional Eval 必须分开

触发评测（Trigger Eval）

问题是：这次该不该调用 Skill？

输入正例、负例、近边界查询，计算 Precision、Recall、F1、Accuracy、Trigger Rate。主要检查 description / metadata。

功能评测（Functional Eval）

问题是：调用后是否把任务真正完成好？

Agent 读取完整 Package 和 fixture，生成任务原生产物，再由断言、独立评分与盲比较判断。

为什么不能混成一个分数？

“很少触发”可能带来高功能均分，因为只处理简单题；“总是触发”可能提升 recall 却打扰无关任务。两个问题的失败原因和修改位置不同。

用户说“帮我做一个 320×240、2 秒循环的庆祝 GIF”，Skill 成功被选中但输出静态 PNG。这是哪类问题？

02
CASE CONTRACT

一个 Functional case 到底要写什么？

字段给谁看作用与例子
user_promptExecutor 可见用户真实请求，不写隐藏答案
input_fixturesExecutor 可见图片、数据、项目目录等真实输入材料
expected_outputGrader 可见任务原生交付物描述，例如 GIF + 说明，不是统一 result.json
content_expectationsGrader 可见尺寸、内容、行为和边界条件
rubricGrader 可见正确性、完整性、专业度、可用性、格式
case_familyCore便于类别回归保护，例如 text-animation
risk / difficultyCore决定最低证据和 Gate 强度
minimum_evidence_tierCore真正证明功能通常至少 E2；确定性检查为 E3
review_recordCore / 人类谁、何时、基于什么意见批准或修订
简化的 TaskCase 示例（注释版）
{
  "case_id": "loop-sparkles-006",
  "user_prompt": "制作一个循环庆祝 GIF……",
  "fixture_refs": ["brand-colors.json"],
  "expected_outputs": ["*.gif", "delivery.md"],
  "content_expectations": [
    "GIF 确实有多帧动画",
    "首尾循环没有明显跳变",
    "使用指定品牌色"
  ],
  "rubric_ref": "rubrics/gif-quality-v1.json",
  "split": "validation",  # 搜索阶段不可见
  "minimum_evidence_tier": "E2"
}
03
AI DRAFT + HUMAN FREEZE

人工审核不是逐题从白纸手写，而是一个可续接的 checkpoint

框架可让 EvalDesigner Agent 从多个维度生成草案，自动检查后导出中文 review.html；用户集中确认、修改或拒绝，再冻结 EvalPlan，后续运行从同一状态续接。

扫描 Package能力、风险、输入与输出
AI 生成草案正负触发 + 功能 case
机器预检重复、泄漏、缺字段、可执行性
中文审核页解释字段与风险
人类修订批准 / 编辑 / 拒绝 / 留意见
冻结计划hash + split + reviewer

机器适合做

批量生成、覆盖能力维度、发现重复、检查字段、标记 oracle 泄漏、校验 fixture 路径。

人适合判断

任务是否真实、有代表性；标准是否过窄；风险是否可接受；validation 是否真的对优化器保密。

冻结后保证

执行条件和评分政策有 hash；候选搜索不能临时换题、改 rubric 或选择有利 case。

审核不会“把项目卡死”

Run 状态在 Core 的 ledger/store 中。审核页面提交后，CLI 导入 并冻结计划，下一阶段继续导出 Executor WorkItem；这正是有意设计的暂停点。

04
RUNNING CASE · FROM DRAFT TO FROZEN

loop-sparkles-006 怎样从 AI 草案变成可信考题？

AI 草案：覆盖能力，不负责定案

EvalDesigner 根据 Package Graph 发现“循环动画、品牌色、尺寸/体积验证、交付说明”四类能力，组合出庆祝 GIF 请求，并附上建议 rubric。

机器预检：先找契约错误

检查 fixture 是否存在、expected output 是否任务原生、case 是否重复、validation 字段是否泄漏、断言是否只检查框架自己生成的字段。

人类审核：修正价值判断

审核者可把“必须恰好 12 帧”改为“至少多帧且循环自然”，避免过窄实现答案；确认品牌色 fixture 真实可用，并决定该 case 属于 validation。

冻结：把选择变成可复现事实

批准内容、split、rubric、assertion policy、reviewer 与时间共同生成 plan hash。搜索开始后不能为了某个候选临时换题。

草案字段审核时发现的问题冻结后的表达
“输出 12 帧 GIF”把一种实现方式当成任务目标多帧动画；时长、尺寸、体积达标；循环过渡自然
“使用蓝色”无法对应输入品牌规范读取 brand-colors.json 并使用指定主/辅色
“生成 result.json”不是用户真正需要的产物*.gif + 可读交付说明；grader 直接读取 GIF
“看起来好看”主观标准不可复核层次、文字可读性、循环平滑、品牌一致性四项 rubric
暂停后如何继续

审核不是退出整个流程。Core 把状态记为 awaiting_review；用户提交决定后导入 review Submission，校验 plan hash，再推进为 frozen。下一章只从冻结版本生成角色隔离的 WorkItem。

05
LEAKAGE BOUNDARY

Executor 绝不能看到什么？

答案信息

assertions、rubric、expected answer、预期胜者。

兄弟输出

no-skill 不能看到 candidate，candidate 不能看到 original。

身份信息

Comparator 看匿名 A/B；Executor 不知道自己是否“应该获胜”。

如果 Executor 看见“grader 会检查是否有 12 帧”，它可能只为了过检查填满 12 帧，而忽略循环是否自然。这叫 ，会让评测从完成任务退化成猜测试代码。

本章面试问答

AI 生成 eval 会不会自说自话？
会有风险，所以 AI 只生成草案；机器先做契约与泄漏检查，人类再确认真实性与代表性。冻结后的 EvalPlan 有 hash 和 review provenance，运行中不能随意漂移。
为什么不直接复制 skill-creator 的 evaluator？
其角色分离与评测原则值得借鉴，但 GEPASE 需要 Core-owned typed WorkItem/Submission、完整 Package 引用、跨文件图、候选谱系和 strict Gate，因此不能把所有状态放进一个 Skill。
Mock 工具什么时候适合？
生产支付、邮件、数据库等不可直接调用时，可用忠实模拟层验证决策和参数，但必须明确环境真实性等级，不能声称 mock 已证明真实服务集成。当前首个公开 canary 优先选择本地可真实运行的 Skill，mock 扩展后置。

本章结论

  • Trigger 与 Functional 回答不同问题，分开计分。
  • Functional case 描述任务原生输出，不再压成 action 标签。
  • AI 批量起草、人类集中冻结是质量与成本的折中。
  • Executor 的最小可见上下文是可信评测的基础。

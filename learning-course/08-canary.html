01
WHY THIS SKILL

为什么它适合作为第一个 canary？

完整 Package

7 个文件可解析出 370 节点、474 条边，足以覆盖 references、scripts 等关系，不是单段 Prompt toy。

任务原生产物

Executor 真正生成 GIF 与交付说明；可以核验帧、尺寸、体积，也能让 Comparator 看视觉差异。

本地可运行

不依赖企业数据库、支付或生产审批，避免首轮闭环同时引入复杂 mock 忠实度问题。

没有先做单独 headroom qualification

按当前项目决策，直接通过完整运行观察优化空间；若搜索停滞或原始 Skill 已接近上限，再补充 headroom 检查，而不是在开始前继续扩张流程。

06
WHAT CHANGED

最终被接纳的不是大改包，而是一个单节点有界修改

修改范围

只修改一个 SKILL.md 节点；这次证据支持该处是高价值范围，所以没有为了展示 package-aware 而强行改 scripts/assets。

如何理解 package-aware

“能改全包”不代表“每轮必须改全包”。Package Graph 和 selector 检查完整上下文，再选择最有证据的最小范围。

项目没有宣称什么

这次结果没有证明 graph-guided 一定优于 random，也没有证明完整 Package 优化普遍优于只改 SKILL.md。应用框架的首要收尾标准是：至少对一个真实 Skill 产生可量化、可复现、经过 held-out 的优化，并清晰呈现证据。

本章面试问答

首个 canary 最有说服力的结果是什么？
不是“生成了 GIF”，而是 original 相对 no-skill 略为负增益，搜索后一个有界候选在冻结 validation 上 3/3 胜、平均 +0.12427，并通过类别回归保护；同时多个看似不错的候选被 strict Gate 拒绝。
为什么 merge child 平均提升还被拒绝是好事？
说明 Gate 没有为了展示成功而放宽规则。它检测到 emoji_animation −0.09144，低于预注册 −0.05 floor，避免平均值掩盖具体能力回归。
真实结果目前最大的局限是什么？
只有一个公开 Skill、8 个 functional case 和 3 个 validation case。它验证了闭环可产生真实增益，不足以说明跨领域普适性；后续应按实际需求扩展更多可运行 Skill，而不是复活旧 action evaluator。

本章结论

  • 原始 Skill 可运行却可能拖累 Agent，paired baseline 很必要。
  • train 最优不等于 validation 最优，严格 Gate 阻止过拟合。
  • 多父 merge 也可能回归，不能继承父代结论。
  • 这次 canary 证明一次真实、量化、可追溯的优化，不夸大为普适定理。

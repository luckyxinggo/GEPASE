COURSE 02 · PACKAGE GRAPH

图不是用来“画架构图”的，而是让每次修改有定位、有边界、有验证强度

文件夹只能告诉我们“有哪些文件”，图还能回答“谁引用谁、谁调用谁、失败可能从哪来、改动会波及哪里”。本章从文件解析开始，逐步理解反向切片、依赖闭包和影响半径。

预计 50 分钟不要求图论基础联系真实代码
01
FROM FILES TO IR

第一步：把异构文件变成稳定的中间表示

为什么要 IR

直接把整个目录拼成一段长字符串，模型只看到模糊文本，还可能被字符数截断。 把“Markdown 标题”“Python 函数”“Shell 命令”“二进制资产”变成有类型、稳定 ID 和来源位置的节点。

PackageSnapshot固定文件与哈希
解析 Frontmattername / description / metadata
解析 Markdownsection / link / code block
解析代码function / import / call
登记资产类型 / 大小 / hash
统一 IRstable node IDs
简化后的节点概念
class PackageNode:
    id: str            # 稳定身份：内容小改时仍可追踪
    kind: NodeKind     # file / markdown_section / python_function ...
    path: str          # 来自 Package 的哪个文件
    span: SourceSpan   # 对应行号或结构范围
    content_hash: str  # 防止修改目标已被偷换
    attributes: dict   # 标题、函数名、语言等类型信息
渐进披露不是截断

Agent 通过 skill_ref 获得完整目录，按需要读取文件；系统记录实际访问成本。它不是先把 Package 拼成字符串再只保留前 26,000 个字符。

03
THREE GRAPH OPERATIONS

三种核心图操作分别回答什么？

反向切片

从失败输出或报错节点逆着边走，寻找可能导致问题的上游节点。回答：可能该改哪里？

依赖闭包

选中修改节点后，把需要一起携带、检查或合并的依赖收全。回答：还必须带上谁？

影响半径

沿正向影响边估算改动可能波及的节点、文件和任务。回答：验证要多严格？

反向切片不会直接断言 render_text() 一定是根因，它只是形成更有证据的候选范围。Analyzer 还要结合错误、实际读取和历史修改收益。

selector_score = 3.0×failure_coverage + 2.0×inverse_distance + 1.4×dynamic_access + 1.2×diagnostic_severity + 0.8×historical_yield + 0.6×exploration − 1.0×fan_out_risk − 1.5×historical_regression
信号白话解释为什么加/减分
failure_coverage这个节点能解释多少失败覆盖更多失败，修改信息密度更高
inverse_distance离失败节点越近分越高减少无关跳跃
dynamic_access真实运行确实读过/执行过比纯静态猜测更有证据
fan_out_risk下游依赖太多改动影响面大，要谨慎
historical_regression过去修改它造成过回归避免反复踩坑

RUNNING CASE · LOOP-SPARKLES-006

把贯穿课程的 GIF 任务先走到“可定位结构”这一步

从本章开始，同一个 case 会一直走到 EvalPlan、隔离执行、评分、GEPA 反思、Patch 和 held-out Gate。这里先只处理 Package，不偷看答案。

上一站带来的问题

slack-gif-creator 是一个包含说明、参考资料、脚本和资产的目录。如果只把七个文件名交给优化器，它无法判断“循环跳变”更可能与验证说明、渲染函数还是配色资产相关。

固定父快照

递归登记七个文件、内容哈希、媒体类型和 Package identity。之后的候选从该只读父快照派生，不原地改公开 Skill。

解析细粒度节点

SKILL.md#verification、质量指南标题、Python 函数、Shell invocation 与 GIF 资产分别成为有类型节点；保留文件和行号来源。

建立静态关系

从 Markdown 路径、Python import/call 和目录包含关系建立边。此时得到“理论上可能影响谁”的潜在结构。

等待运行 overlay

本章还没有真实 trace，所以 observed 边为空。下一次 Executor 读取或执行某节点时，动态图才会把“本轮真的走过”覆盖上来。

三个图操作的最小伪代码
def reverse_slice(graph, failures):
    # 沿影响边的反方向，收集可能导致失败的上游节点
    return graph.walk(starts=failures, direction="reverse")

def dependency_closure(graph, selected):
    # 收集 Patch、merge 和验证时不能遗漏的依赖
    return graph.reachable(selected, relations=DEPENDENCY_EDGES)

def blast_radius(graph, changed):
    # 沿正向影响边估计修改会波及的节点与任务
    return graph.walk(starts=changed, direction="forward")
交给下一章的输出

不是一张 SVG，而是带稳定 ID 的 PackageSnapshot + PackageGraph + diagnostics。EvalDesigner 将据此知道能力边界、可用 fixture、风险节点和任务原生输出类型。

图不能只为了展示。当前工程机制已经实现，但 graph-guided selector 是否比 random、round-robin 或 trace-only 更有效，需要在更多真实失败证据上观察；项目不是论文，不强制大规模消融，但不能把“图已实现”写成“图已普遍证明更优”。

如果一个节点离失败很近，但有极高 fan-out，它应该怎样处理？

本章面试问答

为什么不用向量数据库做失败定位？
语义相似能补充候选，但 Package 依赖包含确定性的包含、引用、调用和运行访问关系。图能提供方向、距离、闭包和影响半径，这些不是单纯向量相似度天然表达的。
动态图和静态图的关系是什么？
静态图描述包的潜在结构，动态 overlay 记录本次 Agent 实际读取、调用和写入。两者联合可避免只相信代码文本或只相信一次运行。
稳定 node ID 为什么重要？
候选迭代时需要比较图差异、记录历史收益、定位 Patch 目标。若每次解析节点身份都随机变化，谱系和 rejected-edit memory 就无法可靠复用。

本章结论

  • IR 让异构文件成为可分析、可追踪、可 Patch 的节点。
  • 图同时包含静态依赖与真实运行访问。
  • 反向切片定位，依赖闭包补全范围，影响半径决定验证强度。

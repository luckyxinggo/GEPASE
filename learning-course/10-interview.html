01
THREE LENGTHS

用三种长度介绍同一个项目

30 秒定位

GEPASE 是一个面向完整 Agent Skill Package 的进化框架。它让真实 Agent 在隔离环境中完成 with-skill 与 baseline 任务，保留原生产物和轨迹；再用 GEPA 式反思与 Pareto 搜索，结合 Package Graph 定位文件并生成有界 Patch。候选只有通过结构、安全、train 和 held-out validation 严格门禁才被接纳。首个公开 GIF Skill canary 在 3 个冻结验证 case 上取得 3/3 胜和平均 +0.12427 skill gain。

2 分钟故事

问题：Skill 写到能运行很快，但缺乏可信方法判断真实增益、回归和修改价值，而且不断补 SKILL.md 会让完整包结构退化。

方法：我把 Heuristic Learning 作为方法论，把完整 Package 当成冻结模型外的可训练状态；使用 GEPA 的任务反馈、反思和 Pareto 搜索；参考 skill-creator 的触发/功能分离与独立角色；参考 SkillOpt 的有界 Patch 和 strict held-out selection；再构建 Package IR/Graph 用于失败切片、mutation scope、依赖闭包和影响分析。

工程：主体是 Python Core + CLI + API，Agent Host 只执行 typed WorkItem。Executor、Grader、Comparator、Analyzer 上下文隔离，EvidenceBundle 保存任务原生产物、trace、usage、timing 和 hashes。

结果与边界：公开 slack-gif-creator canary 的 original 相对 no-skill 略为负增益；4 个候选中只有 1 个通过冻结验证，平均 +0.12427。一个平均验证增益为正的 merge child 因类别回归被 Gate 拒绝。它验证了这次应用闭环有效，但不夸大成跨所有 Skill 的算法定理。

深挖时按证据链展开

  1. EvalPlan 如何冻结任务、split 和 rubric；
  2. WorkItem 可见性如何防 oracle 泄漏；
  3. E2/E3 证据如何证明真实任务而非 action classification；
  4. TaskScoreVector 与 paired delta 如何表达增益；
  5. Package Graph 如何产生 failure slice、closure 和 blast radius；
  6. PackagePatch 如何做 precondition、atomic apply 和 rollback；
  7. GEPA/Pareto 如何选父代、任务与多父合并；
  8. Gate 如何拒绝 train overfit、等分与类别回归。

03
SYSTEM DESIGN QUESTIONS

系统设计高频追问

为什么 Core 与 Agent Orchestrator 要分开？
核心：状态单一所有权。Core 管任务、分数、候选、Gate 和 provenance；Host 只执行工作。这样可切换 Codex、Claude Code 或 API Provider，而不会改变实验语义，也防止重演 S9 双系统。
为什么优化完整 Package，而不只改 SKILL.md？
真实失败可能来自 reference 冲突、脚本 bug、资产缺失、metadata 误触发或跨文件依赖。只改主文档可能掩盖根因并持续堆积。Package IR/Graph 让这些组件进入同一候选与验证契约。
如何确保不同角色不共享上下文？
Core 为每个角色生成字段不同的 typed WorkItem；每个执行使用独立会话与 workspace；Submission 做 artifact/hash/provenance 校验。Comparator 只拿匿名 A/B，Executor 不拿 rubric 或兄弟输出。
为什么不自研 Runtime？
工具和业务环境高度异构。成熟 Agent Host 已能执行真实任务；项目应把复杂度投入评测、证据、图、搜索、Patch 和 Gate，而不是再实现一套通用工具调用框架。
怎样控制运行时间？
只在关键哈希完全一致时复用封存 baseline；按数据依赖并行独立 Executor、Grader、Analyzer；Gate 逐层提前淘汰；只对 train-admitted 候选运行 validation。不会为少量候选过早构建复杂分布式调度。
如何支持私有企业 Skill？
后续可接真实沙箱或忠实 mock 工具，记录调用参数和副作用意图；报告必须声明环境真实性，mock 只能证明决策逻辑和参数，不能证明生产服务集成。首个 canary 先选择本地真实运行以降低变量。
04
ALGORITHM QUESTIONS

算法与评测高频追问

GEPA 在项目里到底做什么？
用 task-level 轨迹和自然语言反馈产生反思式 mutation；用 per-task/per-objective 局部优势与 Pareto 候选池选择父代；在预算内迭代。GEPASE 依赖官方实现，并在外部增加 PackageCandidate、图 selector、PackagePatch 和 Gate。
Pareto 比单一加权总分好在哪里？
避免权重过早抹掉互补优势。一个候选可能视觉质量最好，另一个可靠性最好；只要互不支配就可保留为父代。但工程上仍受池规模与预算限制。
图选择器的分数怎么构成？
当前是可解释加性权重：failure coverage、到失败的逆距离、动态访问、diagnostic severity、历史收益和探索加分；fan-out 风险与历史回归扣分。它用于排序 scope，不替代语义分析或效果 Gate。
为什么有 E0–E3？
它们标记证据强度：E0 静态、E1 计划、E2 真实执行、E3 对 E2 产物的确定性断言。分类让便宜诊断和昂贵功能证明共存，同时禁止用 E1 冒充真实效果。
怎样防止优化器过拟合 evaluator？
冻结 EvalPlan 与 scoring policy；Executor 看不到 oracle；train/validation 分离；候选只在 train 通过后解锁 validation；完全等分不接受；类别与风险 floor 阻止平均值掩盖回归。
TaskScoreVector 为什么包含 package_quality？
任务分上升可能以不可维护、冲突或不安全的包为代价。package_quality 保护结构、引用、可读性和安全；它与任务正确性共同进入多目标和 Gate。
05
FAILURE QUESTIONS

主动讲出失败与纠偏，比回避更有说服力

错误：另写第二套实验系统

S9 重复 Candidate/Evaluator/Search，绕开正式 Core。纠偏：整体删除，恢复 Core-owned state。

错误：真实任务退化成 action classification

模型只返 selected_action，框架生成统一 result.json。纠偏：删除该主链，要求 E2 原生产物和 observed trace。

错误：assertion pass rate 冒充综合质量

公开 Skill 轻易 1.0。纠偏：TaskScoreVector、独立 Grader、blind Comparator 与 skill_gain。

错误：Package 上下文字符截断

违背完整 Package 设计。纠偏：skill_ref 指向完整目录，Agent 渐进读取并记录访问。

错误：等分候选入池

为了候选数放宽接纳。纠偏：至少一个预注册目标严格改善，保护目标不越界，部署必须过 held-out。

面试表达

不要说“前面都做错了”。应该说：早期 evaluator 优化了代理目标而非真实任务，导致工程量与效果脱节；我通过证据审计定位到目标错配，删除旁路系统，并把 acceptance 重新连接到真实 Agent paired evidence。

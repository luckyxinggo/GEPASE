01
THE OPTIMIZATION PROBLEM

GEPA 究竟在优化什么问题？

它面对的是“候选由可读文本组件组成、任务反馈包含自然语言轨迹、完整评测昂贵”的黑盒优化问题。

输入初始 candidate、trainset、valset、Adapter、Reflection LM、预算与策略。
过程选父代和小批任务 → 收集轨迹 → 反思改组件 → 小批筛选 → 全集评测 → 更新状态。
输出候选列表、父代谱系、逐题/逐目标分数、Pareto mapping、最佳 candidate 与运行轨迹。
核心难点

如果只让 LLM 看一个总分 0.63，它不知道失败发生在哪里；如果每次提案都跑全部任务，费用很高；如果只保留平均分第一名，又会丢掉“只在某一类题上特别好”的候选。GEPA 分别用轨迹反思、minibatch screening 和 per-key Pareto memory 回答这三个问题。

寻找 candidate c*，使任务表现更好；但 evaluate(c, task) 是昂贵黑盒，且反馈不仅有分数 r，还有 trajectory τ 与自然语言反馈 f。
候选空间

不是连续向量，而是一个 dict[str, str]：键是可更新组件名，值是文本。比如 {"planner": "…", "solver": "…"}。

评测函数

Adapter 执行 candidate 对一批 DataInst，返回 outputs、scores、可选 objective_scores；反思阶段还需要 trajectories。

搜索信号

单题分数告诉引擎哪里存在局部优势；trajectory 和 feedback 告诉 Reflection LM 为什么失败、改什么可能有效。

状态记忆

GEPAState 保存所有 candidate、父代、逐题分数、逐目标分数、Pareto mapping、预算和 cache，而不是每轮只留一段最新 Prompt。

依据：课程按本项目锁定的 gepa==0.1.4 本地实现核对，入口包括 gepa.core.engine.GEPAEngine、gepa.core.state.GEPAState 与 gepa.proposer.reflective_mutation。可对照 GEPA 官方仓库 和 GEPA 论文。

class MyAdapter(GEPAAdapter):
    def evaluate(self, batch, candidate, capture_traces):
        outputs, scores, traces, objectives = [], [], [], []
        for task in batch:
            output, trace = run_system(task, candidate)
            outputs.append(output)
            scores.append(metric(task, output))
            traces.append(trace if capture_traces else None)
            objectives.append({"correctness": ..., "style": ...})
        return EvaluationBatch(outputs, scores, traces, objectives)
最容易混淆的地方

Adapter 是“把你的系统接给 GEPA”的翻译层，不是 Agent Runtime。它可以调用任何外部系统完成 evaluate，但 candidate 的保存、Pareto state 和搜索循环仍属于 GEPA Core。

03
ONE REFLECTIVE ITERATION

一轮 reflective mutation 实际经过九步

下面严格区分“生成提案”“小批接纳”“完整评测”“进入状态”四个层次。

采样父 candidate 与 minibatch

SamplingStrategy 调用 CandidateSelector 选父代，再由 BatchSampler 选少量 train task。父代可能是 current best，也可能来自 Pareto mapping。

输入：GEPAState + trainset　输出：(parent_idx, minibatch_ids)

重新执行父代，并要求 capture_traces

引擎在本轮 minibatch 上运行父代，得到当前 outputs、scores 与 trajectories。不能只拿旧总分，因为反思需要这批任务的详细行为。

输入：parent + minibatch　输出：parent EvaluationBatch

构造 reflection dataset

把 task input、output、score、trajectory 和 Adapter 提供的反馈整理成反思样本。这里的信息带宽远高于一个 scalar reward。

输出：每个 task 的可读失败证据

选择本轮要修改的 component

ComponentSelector 决定改 planner 还是 solver。官方可以 round-robin 或按策略选择；GEPASE 后续用图选择器替换纯文本组件选择。

输出：components_to_update

Reflection LM 产生新文本

反思器比较失败轨迹与现有组件，输出 new_texts、用于复现的 prompts、raw LM outputs 和 metadata。父 candidate 其他组件保持不变。

输出：尚未验证的新 candidate

在同一 minibatch 上执行 proposal

新 candidate 再跑这批任务，得到 subsample_scores_after。这是便宜的 early screen，不是完整效果结论。

比较：before scores ↔ after scores

AcceptanceCriterion + SelectionStrategy

Criterion 判断是否改善；SelectionStrategy 从一批提案中决定哪些值得进入完整评测。0.1.4 默认接纳语义是 strict improvement，默认选择所有通过项。

输出：selected proposals 与明确拒绝原因

selected proposal 跑完整 valset

只有小批筛选通过的提案才进行 full evaluation；EvaluationCache 以 candidate hash + example id 避免重复执行。

输出：逐 val_id 分数与逐 objective 聚合

写入 GEPAState 并更新 frontier

追加 candidate、父代索引、发现时预算、逐题分数和目标分数；更新 instance/objective/cartesian frontier，触发 callback，并可能调度 merge。

输出：可保存、可恢复的新搜索状态

WHY THIS ORDER

先小批找方向，再全集确认

如果直接对每个 LLM 提案跑全量评测，预算会浪费在明显无效修改上；如果只信 minibatch，又容易过拟合。GEPA 用两级评测平衡成本和可信度。

但注意：官方 GEPA 的 valset 是搜索引擎内部完整评测集，不自动等同于 GEPASE 的部署 held-out validation。后者在搜索之外另设严格 Gate。

04
WORKED ITERATION

手算一轮：为什么总分变化很小，候选仍值得保留？

设 seed candidate S 在三个任务上的分数是：

任务S 分数轨迹暴露的问题
T1 · 文字动画0.55没有根据画布缩放字号
T2 · 循环过渡0.82已经较好
T3 · 文件压缩0.75执行了体积检查
①

父代选择器选 S，minibatch 抽到 T1、T2。

②

Reflection LM 根据 T1 trace 把 planner 从“渲染文字”改为“先测量文本边界，超出时逐步缩小字号，再渲染”。得到候选 A。

③

A 在 minibatch 上变成 T1=0.83、T2=0.80。合计从 1.37 变为 1.63，严格改善，进入 full eval。

④

full eval 得 A=[0.83, 0.80, 0.70]，平均 0.7767；S 平均 0.7067。A 是 current best。

⑤

后来候选 B=[0.60, 0.86, 0.90]，平均 0.7867，比 A 更高；但 A 仍是 T1 champion。若只留平均第一，T1 的局部优势就丢了。

这正是 GEPA 引入 per-instance frontier 的动机：A 可继续作为针对 T1 失败的父代，甚至与 B 的互补组件发生 merge。下一章会把这里的“champion mapping”和传统多目标 Pareto 区分开。

def add_candidate(parent_ids, candidate, full_eval):
    idx = len(state.program_candidates)
    state.program_candidates.append(candidate)
    state.parents.append(parent_ids)
    state.scores_by_task.append(full_eval.scores_by_id)
    state.objectives.append(mean_by_objective(full_eval.objective_scores))

    for task_id, score in full_eval.scores_by_id.items():
        if score > state.best_score_for_task[task_id]:
            state.best_score_for_task[task_id] = score
            state.champions_for_task[task_id] = {idx}
        elif score == state.best_score_for_task[task_id]:
            state.champions_for_task[task_id].add(idx)

    update_objective_and_cartesian_frontiers(idx, full_eval)
为什么 cache 是算法的一部分？

搜索反复评测相同 candidate/task。0.1.4 的 EvaluationCache 使用候选内容哈希和 example ID 作为键；缓存命中不增加实际 metric call。否则预算统计会把重复工作当成新探索。

06
MERGE IN OFFICIAL GEPA

官方 merge 不是把两个最高分 Prompt 拼起来

从 frontier dominators 中找两条分支

父代不能互为祖先，必须存在共同祖先；共同祖先的 aggregate score 不能高于两个后代。

比较每个 predictor/component 相对祖先的变化

如果只有一个后代修改某组件，取该修改；如果双方都改且不同，0.1.4 的通用 merge 依据 aggregate score 或平局随机选择。

用父代优势区域选 subsample

从 parent 1 更好、parent 2 更好、二者平局的 val IDs 中抽样，检查 child 是否至少不差于两个父代。

通过后才进行 full eval 并写入多父谱系

merge child 仍是新 candidate；它不会自动继承父代的分数。

为什么 GEPASE 不能直接照搬文本 merge？

Package 组件存在文件引用、函数调用和依赖闭包。两个父代都改同一文件时不能只按 aggregate score 选择文本；GEPASE 增加 common lineage root、source snapshot、contribution subgraph、dependency closure、conflict set 与 typed resolution，再让 child 重新跑 Gate。

OFFICIAL GEPA VS GEPASE

哪些由官方 GEPA 提供，哪些是 GEPASE 外围新增？

能力官方 GEPA 0.1.4GEPASE 的处理
Candidatedict[str,str] 文本组件不可变 PackageCandidate；component 是稳定图节点/内容投影
Feedbackscore、trajectory、Adapter feedbackExecutionBundle、TaskScoreVector、grader/comparator/analyzer、evidence refs
组件选择通用 component selectorGraph-guided/random/round-robin/trace selector
MutationReflection LM 返回 new textsAgent/LLM 返回 typed PackagePatch，带 precondition 和 edit budget
Frontierinstance/objective/hybrid/cartesian mapping官方 state 的 snapshot + train pool/deployable frontier 分离
Acceptance小批 criterion + full val evaluationGate 0/1/2/3；held-out validation 在搜索之外严格保护
Merge共同祖先上的文本 predictor 合成同 Package/snapshot/root + closure/conflict/typed child
Runtime由 Adapter 提供 evaluateAgent Host 外置；Core 用 WorkItem/Submission 接收真实证据
命名陷阱：valset ≠ 自动 held-out

官方 GEPA 在搜索中用 valset 更新 frontier、选 best candidate；它可能被多轮搜索间接利用。GEPASE 的 frozen held-out validation 只对 train-admitted candidate 解锁，并由 strict Gate 决定 deployable 状态。课程后续凡说“部署验证”，指后者。

请完整描述 GEPA 一轮 reflective mutation
选择父代和 minibatch；带 trace 执行父代；构造 reflection dataset；选择组件；Reflection LM 产生新文本；在同一 minibatch 评测；AcceptanceCriterion 与 SelectionStrategy 选出提案；selected proposal 跑 full valset；写入 candidate、父代、逐题/目标分并更新 frontier、预算和 cache。
GEPA 为什么比只用标量 reward 更适合文本组件优化？
文本与 Agent 轨迹天然包含可读语义。GEPA 把 input、output、trajectory 和反馈交给 Reflection LM，使修改有具体因果假设；score 仍负责验证，而不是让语言反思自我批准。
官方 GEPA 的 Adapter 和 GEPASEAdapter 有何关系？
概念上都是领域翻译层。GEPASE 把 PackageCandidate components 与真实 Eval Core 产生的 CandidateEvaluation 映射给官方 state/selector；它本身不调用 Agent Runtime，实际执行通过 Core work queue 和 Agent Host 完成。
为什么 GEPASE 不直接调用 GEPAEngine 完成所有状态转换？
GEPAEngine 的通用 candidate/new-text/valset 语义不足以表达 Package snapshot、typed Patch、结构安全 Gate、真实角色 evidence、train/held-out 分离与 dependency-aware merge。GEPASE 复用锁定的 state/selector/算法骨架，在外层保持这些强契约。

本章必须真正掌握的五点

  • GEPA candidate 是可更新文本组件字典，Adapter 把领域系统接入 evaluate。
  • 一轮 mutation 包含父代小批轨迹、反思提案、小批筛选、完整评测和 state 更新。
  • GEPAState 保存候选、谱系、逐题/目标分、frontier、预算和 cache。
  • merge 依赖共同祖先与组件差异，child 必须重新评测。
  • GEPASE 使用官方骨架，但把 deployment held-out、PackagePatch 和图依赖放在外层。

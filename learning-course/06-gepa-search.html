GEPASEAdapter 的责任边界（概念伪代码）
class GEPASEAdapter(GEPAAdapter):
    def evaluate(self, gepa_view, batch):
        candidate = self.candidate_store.resolve(gepa_view)
        records = self.evidence_provider.load_or_dispatch(
            candidate=candidate,
            cases=batch,
            require_tier="E2",
        )
        return EvaluationBatch(
            scores=project_objectives(records),
            trajectories=keep_task_feedback(records),
        )

    # Adapter 不执行通用 Agent Runtime，也不裁决 deployable
最容易混淆的边界：GEPA 的 valset 不等于 GEPASE 最终 held-out

在官方搜索引擎里，valset 用于完整评测、维护 frontier，搜索过程会反复利用这些结果。GEPASE 的 frozen held-out validation 是部署 Gate 的最后一道保密考卷；只有 train-admitted 候选才可解锁，而且结果不能反哺同一轮提案。

反思器不是裁判

它可以提出因果假设，但是否有效由新候选的 paired train 与 held-out validation 决定。失败反思必须保留“假设”身份。

04
LINEAGE + MERGE

多父合并发生在同一个 Skill Package 的谱系内部

允许

同一个原始 Package 派生的多个父候选，在 package identity、schema 和基础快照兼容时合并。

明确禁止

禁止跨不同 Skill Package 合并，例如把 slack-gif-creator 和另一个不同 Skill 当父代。它们的能力、文件语义和评测契约不一致。

合并不是复制两份文本拼起来。Core 计算 、检测同节点冲突，必要时由独立 merge proposer 生成结构化 child Patch，然后 child 从 Gate 0 重新开始。

05
RUNNING CASE · ONE SEARCH ITERATION

loop-sparkles-006 的失败怎样推动一次 Package mutation？

选择父代与训练任务

从 train pool 的 Pareto/champion coverage 中抽样父代；按预算选取能暴露当前弱点的 minibatch，而不是看 held-out case。

重放父代证据

相同环境、模型、EvalPlan 和 scoring policy hash 下复用已封存 reference；对父代任务读取分数、GIF、trace 与 grader/comparator 理由。

ASI 聚合失败

把“循环跳变”“交付前未调用验证脚本”“验证说明弱”连接到 SKILL.md#verification 与相关脚本节点，生成仍待验证的因果假设。

图 selector 确定 bounded scope

综合 failure coverage、图距离、observed access、fan-out 与历史回归，选择一个或一组允许修改的节点。

Proposer 生成 typed Patch

LLM/Agent 只在给定 scope 内提出 add/delete/replace 等操作；Core 检查 schema、precondition，并在隔离 snapshot 上 materialize child。

先 train，再决定是否解锁 held-out

严格改善且保护线不越界才成为 train-admitted；最终 deployment Gate 不由 GEPA reflection 或 parent selector 决定。

GEPA 保留局部冠军与父代选择

避免只围绕单一平均赢家搜索。

GEPASE 新增Package / Graph / Patch 契约

让建议成为可定位、可校验、可回滚的完整包候选。

Strict Gate 保留部署裁决权

train Pareto pool 与 deployable frontier 永不混写。

交给下一章的输出

不是“请把 Skill 改好”这一句提示，而是：选定父候选、failed case evidence、ASI 假设、graph-ranked nodes、mutation budget 和 rejected-edit memory。下一章把它变成真正的 PackagePatch。

06
BUDGETED SEARCH

预算决定“最多探索多少”，不是候选越多越好

执行预算

可运行多少 paired Executor case；这是最昂贵部分。

候选预算

最多提案、train-admit 和 validation 的候选数。

角色预算

Grader、Comparator、Analyzer、Reflection 各自的调用上限。

当前策略不是追求大规模矩阵

先在一个公开、可本地运行、并不太简单的 canary 上跑通可信闭环。候选不多时，证据复用和依赖级并行已经足够；无需为尚不存在的规模设计复杂分布式系统。

本章面试问答

GEPA 式搜索相比一次性改 Prompt 好在哪里？
它保留 task-level 反馈和完整轨迹，反思可以针对失败；Pareto 池保留局部优势；候选有谱系和预算；每次修改通过真实任务与 Gate 验证，而不是依赖一次自评。
为什么多父合并重要但不能直接接受？
互补改进有组合价值，但也可能产生冲突、重复规则或类别回归。合并 child 是一个新候选，必须计算依赖闭包并从 Gate 0 到 held-out 全部重跑。
如何避免反复提出同一种坏修改？
RejectedEditStore 保存 Patch、目标节点、失败 Gate 和回归证据；selector 的 historical_regression 也会降权相关节点。

本章结论

  • 任务级自然语言反馈比单一 reward 更能指导结构化修改。
  • Pareto 保留互不支配的候选与局部优势。
  • 多父合并只允许同 Package 谱系，child 必须重新验证。
  • 预算让搜索可控、可比较、可复现。

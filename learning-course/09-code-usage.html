02
READING ORDER

推荐源码阅读顺序

1. 先读权威事实源

state.md：定位、契约、阶段状态、有效结论与纠偏历史。

2. 再读交换类型

evals/work_items.py、evals/functional.py、evals/scores.py、optimizer/candidate.py、mutation/models.py。

3. 跟一次真实 case

从 R3 work item 找到 ExecutionBundle、grader/comparator submission、score vector 与 ledger 记录。

4. 跟一个候选

从 reflection、graph selector、PackagePatch 到 materialized child、Gate decision 和 rejected/accepted 状态。

5. 最后看 CLI 与报告

它们应只调用 Core 类型和状态，不应再实现一套 Candidate/Evaluator/Search。

阅读原则：类型定义告诉你“允许什么”，artifact 告诉你“这次实际发生了什么”

只读代码容易把尚未跑过的分支误认为已验证效果；只看报告又无法判断边界是否由类型和 Gate 保证。两条证据要相互核对。

Agent-native 默认模式

Core 导出 typed WorkItem；Codex/Claude Code 等 Host 按角色隔离执行；通过 CLI 提交。用户不需要为了普通运行再配一个 Provider Key。

可选 Headless Provider

配置 OpenAI-compatible / DeepSeek 等后端后，可让特定角色自动调用指定模型。它是替换执行后端，不改变 WorkItem、证据和 Gate。

05
PYTHON API

Python API 应该围绕类型组合，而不是调用网页自动化

概念化 Python API 主链
from gepase.package import PackageLoader
from gepase.evals import EvalPlanStore, FunctionalPipeline
from gepase.optimizer import EvolutionController

# 1. 输入只读 Package，得到快照与图
snapshot = PackageLoader().load("path/to/skill")

# 2. 使用已审核、已冻结的评测计划
plan = EvalPlanStore().load_frozen("eval-plan.json")
pipeline = FunctionalPipeline(plan=plan, package=snapshot)

# 3. 导出工作；Host 完成后再 ingest，不共享角色上下文
work_items = pipeline.export_executor_work()
records = pipeline.ingest_submissions("submissions/")

# 4. Core 依据分数、图、Patch 和 Gate 推进候选状态
controller = EvolutionController(...)
decision = controller.advance(records)
这段代码是教学映射，不是可复制的稳定 API 示例

它展示模块边界；准确导入名和构造参数应以当前包导出与测试为准。课程的机器 Gate 会防止把概念伪代码误写成 reproduction 命令。

06
EXTENSION RULES

以后扩展私有 Skill 或 mock 时，哪些接口不能破坏？

保留任务原生输出

mock_send_email 可记录参数，但输出仍应是邮件决策与正文证据，不能退化成 selected_action。

声明环境真实性

明确是真实外部系统、沙箱、录制回放还是模拟；报告不得把 mock 结果说成生产集成成功。

保持 Core-owned state

新 Host/Provider 只实现 WorkItem → Submission，不另建 Candidate、Evaluator 或 Gate。

本章面试问答

为什么项目必须同时提供 CLI 和 Python API？
CLI 便于开源用户、Agent Host 和可复现实验调用；Python API 便于嵌入其他系统与测试。两者共享同一 Core，避免业务逻辑只存在命令脚本中。
如何避免再出现第二套实验系统？
Candidate、score、Gate、ledger 与 lineage 只有 Core 类型；Host 层只处理 typed work/submission。CI、schema 和阶段 Gate 检查禁用旧 action 字段与重复入口。
项目为什么保留大量 artifact？
真实产物、trace、hash、Gate report 和 lineage 是可复现证据。应区分发布所需小型 evidence 与可清理的历史运行缓存，不能把 artifact 当无意义日志，也不能全部提交仓库。

本章结论

  • 先沿交换类型和真实 case 读代码，不从目录顺序硬啃。
  • CLI 与 Python API 共享独立 Core。
  • Agent-native 与 Headless 只差角色后端，不改变隔离和裁决。
  • 新 Runtime/Mock 接入必须坚持任务原生输出与 Core-owned state。

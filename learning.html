Graph-Enhanced Package-Aware Skill Evolution

从“会写 Skill”到“会训练 Skill Package”

这份手册解释 GEPASE 的理论来源和实现映射。核心问题不是让 LLM 把一份 Markdown 写得更漂亮，而是把完整 Skill Package 视为冻结 Agent 的外部可训练状态，用真实任务、执行轨迹、结构化编辑和独立验证形成可复现的学习闭环。

02

先建立算法地图

不同工作解决的是闭环中的不同问题，不能把它们简单拼成模块名。

Search

GEPA

负责多候选搜索、任务级多样性、反思式变异、候选融合和预算控制。

Stability

SkillOpt

负责有界编辑、验证门控、拒绝编辑记忆和跨 epoch 的稳定更新。

Representation

Package Graph

负责把“改哪个文件”提升为失败归因、影响分析、闭合子图修改和安全融合。

Evaluation

skill-creator

提供 with-skill/no-skill、重复运行、assertion、盲评和成本—质量分析思想。

Evidence

SkillLens

提醒我们 Skill 存在负迁移，生成能力、消费能力和模型规模不能直接等同。

Engineering

Darwin + HL

贡献 Git ratchet、显式记忆、回归测试、失败历史和人在回路的工程方法。

一句话关系： GEPA 决定“探索哪些候选”，SkillOpt 决定“一次允许怎样改、什么情况下保留”，Package Graph 决定“失败与哪些组件有关、如何安全地改和合并”，Eval 决定“所谓提升是否可信”。
03

GEPA：项目的外层搜索骨架

Reflective evolution 的价值，在于把完整轨迹保留为可推理的学习信号。

3.1 GEPA 在优化什么？

设一个 AI 系统由若干可修改文本组件构成，候选记为 Φ。对于任务实例 x，系统执行后产生轨迹 τ、输出 y、数值评分 μ，以及自然语言或结构化反馈 μf。GEPA 的目标不是通过反向传播更新模型权重，而是在有限评测预算内寻找更好的文本候选。

Φ → rollout(x) → { trajectory τ, output y, score μ, actionable feedback μf } → reflect → Φ′

标量 reward 丢失了什么？

只知道 0 分，无法知道是触发失败、引用没读、脚本报错、输出格式错误，还是任务知识不足。

ASI 提供了什么？

错误断言、stderr、工具轨迹、实际输出、期望输出、成本、图切片等可操作信息，让 LLM 像工程师一样定位问题。

3.2 核心循环

候选选择从 frontier 采样父代
任务采样抽取反馈 minibatch
Rollout执行并收集轨迹
反思变异修改一个或多个组件
快速评测判断是否有提升
全量验证更新池与 frontier
面试易错点： GEPA 不是“随机遗传算法 + LLM”。变异不是盲目字符扰动，而是 LLM 阅读轨迹和反馈后的定向诊断；遗传性主要体现在候选继承、变异、融合与多代谱系。

3.3 Per-key Pareto Frontier 到底是什么？

当前 GEPA 为每个 frontier key 记录 best-in-class 候选。key 可以是验证样本、显式目标，或者两者组合。候选在多少个 key 上处于最佳，会影响它被选作父代的概率。

候选任务 T1任务 T2任务 T3任务 T4解释
P01.00.20.40.3T1 专家
P10.71.00.50.4T2 专家
P20.40.61.00.9T3/T4 专家
P30.80.80.80.8平均很好，但没有任何 key 第一

在 per-key frontier 下，P0、P1、P2 会被保留，因为它们至少在一个任务上最好；P3 可能落选。可是从严格多目标优化看，P3 未必被任何候选完全支配。因此：

  • instance frontier：每个验证任务一个 key，适合大量任务。
  • objective frontier：每个 accuracy、cost、latency 等目标一个 key。
  • hybrid frontier：同时考虑任务和目标，GEPASE 的初始主设置。
  • true non-dominated selector：保留全部非支配候选，可加入 crowding distance 避免候选坍缩。

3.4 反思式变异

当前候选组件、任务 Prompt、Agent 输出、工具轨迹、分数、断言、stderr、成功样本中应该保留的行为，以及同类 rejected patches。
优化模型判断失败是知识缺失、路由错误、脚本缺陷、触发错误、格式不明确还是过度约束，并定位应修改的最小组件。
原始 GEPA 通常输出更新后的文本组件；GEPASE 将其约束为带证据、前置条件和预算的 PackagePatch。

3.5 系统感知融合与 DAG

如果父代 A 擅长任务集合 SA，父代 B 擅长 SB，融合希望组合互补组件。由于一个新候选可能有多个父节点，候选谱系天然是 DAG，而不是严格的树。对 Package 来说，直接按文件替换有风险：复制脚本时可能遗漏引用它的说明、测试和依赖。因此 GEPASE 融合的是依赖闭合子图。

父代 A触发与说明更好
父代 B脚本与错误处理更好
闭合子图融合检查接口与依赖冲突
子代 C重新通过全部 Gate

3.6 用当前 GEPA API 表达 GEPASE

Python · 概念性集成骨架
from gepa.optimize_anything import (
    optimize_anything, GEPAConfig, EngineConfig, ReflectionConfig
)

seed = {
    "metadata_and_routing": load_routing(seed_path),
    "skill_instructions": load_skill_md(seed_path),
    "reference_bundle": load_references(seed_path),
    "script_bundle": load_scripts(seed_path),
}

config = GEPAConfig(
    engine=EngineConfig(
        max_metric_calls=200,
        candidate_selection_strategy="pareto",
        frontier_type="hybrid",
        acceptance_criterion=ValidationGatedAcceptance(),
        cache_evaluation=True,
    ),
    reflection=ReflectionConfig(
        reflection_lm="provider/strong-reflection-model"
    ),
)

result = optimize_anything(
    seed_candidate=seed,
    evaluator=evaluate_package,
    dataset=train_tasks,
    valset=validation_tasks,
    objective="Improve task utility while preserving package integrity.",
    config=config,
)

export_package(result.best_candidate, output_dir="best_skill_package")

代码中的 ValidationGatedAcceptance、load_routing 和 evaluate_package 是 GEPASE 需要实现的扩展；接口细节应以项目锁定的 GEPA 版本为准，并通过集成测试防止上游 API 演化导致结果漂移。

SkillOpt：让更新过程稳定下来

GEPA 擅长多样性搜索，SkillOpt 强调训练纪律与验证门控。

4.1 深度学习类比不是装饰

权重训练SkillOpt在 GEPASE 中

Forward目标模型 RolloutAgent + tools + scripts 的真实执行
Gradient signal轨迹反思与编辑建议ASI + failure subgraph
Learning rate每步文本编辑预算Patch 数量 + graph edit budget
Validationheld-out selection gate结构硬 Gate + 完整 validation
Momentum / slow stateslow/meta update后续扩展的跨 epoch optimizer memory

4.2 为什么 full rewrite 容易退化？

归因困难

一次改十处，分数变化无法归因，也无法学习哪些编辑真正有效。

灾难性遗忘

修复新失败时覆盖已经有效的规则、格式或工具使用习惯。

局部过拟合

把 minibatch 的具体实体、路径或答案写进 Skill，validation 立即暴露。

4.3 GEPASE 的结构化 Patch

JSON · PackagePatch 示例
{
  "parent_snapshot": "sha256:8cc...",
  "edit_budget": 2,
  "operations": [
    {
      "op": "move_node",
      "node_id": "section:common-domain-rules",
      "to": "references/domain.md#rules",
      "evidence_eval_ids": ["E17", "E24"],
      "expected_benefit": "Reduce always-loaded context."
    },

}
SkillOpt 最重要的启发不是“把训练术语搬到 Prompt”，而是：每次更新保持足够小、证据足够清楚、失败编辑能被记住，并由独立的 held-out 数据决定是否保留。
05

SkillLens：Skill 有用，不代表总是有用

模型生成 Skill 的效用需要在完整生命周期中验证。

负迁移

Skill 可能把 Agent 约束到错误流程、引入过时知识、造成过度工具调用，最终比 no-skill 更差。

Producer ≠ Consumer

一个模型很会从经验提炼 Skill，不代表它最会使用 Skill；模型规模和 baseline 强弱也不能直接预测收益。

在 GEPASE 里的落地

  • 任何效果结论都包含 no-skill、seed skill 和 optimized skill。
  • 单独报告 negative transfer rate，而不是让平均分掩盖退化类别。
  • 在预算允许时做 cross-model 或 cross-harness transfer。
  • 结构 rubric 只作为 gate 和诊断，不能替代真实任务 utility。
  • 记录优化模型、目标模型和 Judge 模型三个角色，防止概念混淆。
06

Anthropic skill-creator：Eval 基础设施

它最值得学习的不是写作模板，而是比较与分析工作流。

渐进披露

metadata 始终可见；SKILL.md 在触发后进入上下文；references、scripts 和 assets 按需读取或执行。

Benchmark

同一 Prompt 运行 with-skill 和 baseline，多次重复，统计 pass rate、duration、tokens 及方差。

Blind comparison

比较器不知道 A/B 哪个是新版本，降低“新版本应该更好”的期待偏差。

Analyzer

识别永远通过的无区分度 assertion、高方差 case，以及效果提升与成本增长的权衡。

GEPASE 必须对 assertion 做“反例测试”：把明显错误的输出喂给断言，如果仍能通过，说明评测本身正在被优化器钻漏洞。

10

GEPASE：算法如何拼成闭环

外层负责探索，内层负责稳定，图负责结构信用分配，Eval 负责真相。

10.1 一轮完整优化

  1. 从 hybrid Pareto pool 选择父代 PackageCandidate。
  2. 采样一组失败、退化或高不确定性的训练任务。
  3. 先执行 E0 静态检查与 E1 推演式 paired rollout；只让有希望或高不确定候选晋级 E2 子智能体 Forward Test 和 E3 可执行断言。
  4. 严格区分 E1 planned edge 与 E2/E3 observed edge，再与静态 Package Graph 合并生成 fidelity-aware failure subgraph。
  5. GraphGuidedSelector 在编辑预算内选择 mutation scope。
  6. LLM 读取相关候选片段、ASI、成功行为和 rejected history，提出 PackagePatch。
  7. Patch Engine 在临时 snapshot 应用 Patch。
  8. 运行 schema、引用、语法、测试、安全等廉价 Gate。
  9. 运行 minibatch 前后对照；无希望则拒绝。
  10. 运行完整 held-out validation；满足接受规则才加入池。
  11. 更新 per-task / per-objective frontier、候选 DAG、成本和负反馈记忆。

10.2 候选接受伪代码

Python · 概念性伪代码
def should_accept(parent, proposal, state):
    candidate = patch_engine.apply(parent, proposal.patch)

    # 廉价硬门控先执行，避免浪费 LLM 调用
    hard = validators.run_all(candidate)
    if not hard.ok:
        rejected_store.add(proposal, reason=hard.failures)
        return False

    mini = paired_eval(parent, candidate, proposal.minibatch, tiers=["E0", "E1"])
    if not mini.promising:
        rejected_store.add(proposal, reason=mini.delta)
        return False

    # 功能接受必须由预注册的 E2/E3 证据决定
    val = full_validation(candidate, minimum_tier="E2")
    if val.breaks_regression_floor:
        rejected_store.add(proposal, reason=val.regressions)
        return False

    return val.is_epsilon_non_dominated_and_useful()

10.3 为什么它不是简单套壳？

  • GEPA 不原生理解 Skill Package 的文件语义、依赖闭包和脚本副作用。
  • SkillOpt 不负责多父代 Pareto 探索，也不联合训练完整目录。
  • Package Graph 不只是报告，它改变 component selection、edit budget、validation intensity 和 merge。
  • 独立 Python Core 管理 Evidence、候选、图、Pareto 与 Gate；Agent Orchestrator Skill 只负责领取任务、委派子智能体和回写结果。
  • MultiFidelityEvalEngine 把 E0 静态、E1 推演、E2 子智能体和 E3 可执行证据统一到同一 schema，同时禁止 planned/observed 混淆。
  • 项目贡献能通过等预算消融验证，而不是依靠架构图叙事。
11

Package Graph：什么时候真正有用？

图是结构化中间表示，重点是可解释的 slicing、closure 和 impact analysis。

11.1 节点与边

节点

frontmatter 字段、SKILL 章节、instruction block、reference chunk、script module/function、asset、eval case、output artifact。

边

contains、references、imports、calls、declares、produces、reads、executes、covers、fails_at、contributes_to。

11.2 失败切片示例

Eval E17 失败空行解析 assertion
parse_rows()动态 executes + stack frame
脚本调用说明SKILL.md references
无关领域文档未访问，不进入 scope

从失败 assertion 反向沿 produces、calls、references、executes 等边扩展，得到最小相关子图。LLM 只看到相关函数、调用说明、对应测试和必要邻居，而不是整个 Package。这同时降低上下文成本和无关修改概率。

11.3 Graph-guided selector

priority(v) = failure_coverage × expected_impact × uncertainty_bonus ÷ (1 + mutation_risk + historical_regression)

这个公式是可替换的启发式，不应包装成未经验证的理论定理。真正的证据来自等预算消融：random、round-robin、trace-only 与 graph-guided 在 accepted improvement、metric calls、回归率和最终 test utility 上谁更好。

为什么第一版不用 GNN？ 单个 Skill Package 图规模小，监督样本也少。GNN 会增加训练数据需求和解释成本，却未必优于透明规则。只有积累大量跨 Skill 的 graph—patch—outcome 数据后，学习式 selector 才合理。
12

Eval 与统计：项目可信度的核心

优化器可以很朴素，评测不能含糊。

12.1 三段数据为什么必须隔离？

Train

可以进入反思上下文，用来发现失败模式和产生 Patch。

Validation

决定候选是否接受和哪一个是 best candidate，但不直接告诉 proposer 正确答案。

Test

优化冻结后才运行，只用于最终结论，不能反复查看后继续调系统。

12.2 多目标指标

类别主要指标用途
Task utilitypass rate、task-specific score主要效果结论
Triggerprecision、recall、F1判断 Skill 是否在正确场景生效
Efficiencytoken、cost、latency、tool calls避免用无限成本换准确率
Structurebroken links、orphans、tests、complexity门控与维护性
Continualregression、negative transfer、accepted yield衡量持续优化稳定性

12.3 统计最小要求

  • 同一任务、同一环境、同一模型配置的 paired before/after。
  • 二元结果报告 paired bootstrap 95% CI，必要时使用 McNemar。
  • 至少三个独立优化种子，报告平均值与方差。
  • 报告总 metric calls、LLM calls、token、美元成本和时间。
  • 主表展示所有 Skill，不只展示最好案例。
  • 失败候选和不显著结果也进入公开 artifact。

12.4 什么才算项目成功？

不是“LLM 生成了一个新版本”，而是：在未见 test 上，GEPASE 相对 seed skill 有稳定正向提升；在等预算下相对 vanilla GEPA 或随机 selector 更高效或更少回归；所有最终 Package 仍然结构合法、可执行、可审计。若图引导没有收益，诚实的负结果和原因分析仍有价值，但不能继续宣称图算法有效。

13

面试思考问答

回答要围绕问题定义、设计取舍、实验依据和局限，不要堆术语。

1. Skill 优化和 Prompt 优化有什么本质区别？
Skill 的核心仍包含上下文文本，所以与 Prompt 优化同源；区别在于 Skill 是可复用、可触发、可包含脚本和资源的程序化 Package。优化对象不只是指令措辞，还包括加载路由、工具策略、参考知识、可执行代码和依赖一致性，因此更接近外部可训练 Agent policy。
2. 为什么以 GEPA 为主体，而不是直接使用 SkillOpt？
SkillOpt 对单文档的局部稳定更新很强，但 GEPASE 还需要保留在不同任务上具有互补优势的多个候选，并进行多父代融合。GEPA 的候选池、per-key frontier、反思变异和 merge 更适合作为外层搜索；SkillOpt 的有界编辑和 validation gate 用于增强其稳定性。
3. GEPA 为什么可能比只优化最高平均分候选更好？
平均分会掩盖专长。某候选可能只修好了少数困难类别，平均提升不大，但这些局部能力可以在后续融合或继续变异中转化为更强系统。per-key frontier 为这些候选保留进化机会，减少贪心搜索过早收敛。
4. GEPA 的 Pareto 是严格的非支配前沿吗？
默认不完全是。当前 GEPA 的 per-key frontier 保存至少在某个验证样本或目标上达到 best-in-class 的候选。一个各方面都不错但从未单项第一的非支配候选可能被遗漏。GEPASE 会比较 hybrid per-key 与 true non-dominated selector，并考虑 crowding distance。
5. 图算法为什么不是为了包装项目？
图直接影响四个决策：失败相关组件选择、Patch 的依赖闭包、公共接口修改的验证强度、多个父代的子图融合。如果移除图只影响可视化，那它就是装饰；因此必须通过 random、trace-only 和 graph-guided 等预算消融验证。
6. 为什么不用 GNN？
单包图小、跨 Skill 标注数据少，透明启发式更便于调试与归因。GNN 只有在积累足够多 graph—patch—outcome 历史后才可能优于手工 selector。第一版引入 GNN 会增加复杂度但缺乏可信训练信号。
7. 如何防止 LLM 通过修改 Skill 钻 Eval 漏洞？
严格隔离 test；对 assertion 做反例和 mutation testing；不把验证答案直接提供给 proposer；监控候选是否写入任务实体；使用多样任务和分组切分；对 suspicious shortcut 设置规则；保留独立 Judge 和人工抽查。
8. 为什么不能只用 LLM-as-a-Judge？
Judge 会受措辞、长度、顺序和自我偏好影响，还可能与 proposer 共享模型偏差。可执行任务应优先使用脚本、文件和 assertion 验证；Judge 仅评价难以程序化的质量，并尽量盲化候选身份、使用独立上下文和校准样例。
9. 有界 Patch 如何对应 SkillOpt 的 textual learning rate？
学习率不再是连续数值，而是一次允许的操作数、修改节点数、图边变化数、token diff 和公共接口风险。早期可以较大，后期逐渐收缩；高风险或高 fan-out 节点自动降低预算并提高验证强度。
10. 如何衡量图引导带来的样本效率？
在相同 target/optimizer 模型、任务、proposal 次数和 metric-call 预算下，比较达到相同 validation score 所需调用数、accepted-improvement yield、无效 Patch 比例、回归率和最终 test utility。不能只比较墙钟时间，因为并发配置可能不同。
11. 如何避免灾难性遗忘？
把历史能力固化为 regression tasks 和 golden traces；使用小步编辑；完整 validation 检查旧类别；对公共节点提高验证覆盖；记录 rejected edits；定期提出 compression 而不是只追加规则。它不能保证零遗忘，但能将遗忘变成可检测和可回滚的问题。
12. Package merge 最大的技术风险是什么？
组件之间存在隐式接口。只复制一个脚本可能遗漏调用说明、依赖和测试；只复制文档可能引用不存在的文件。GEPASE 因此融合依赖闭合子图，先做静态冲突检测，再对冲突部分生成结构化 resolution patch，最后重新通过全部 Gate。
13. 如果图引导实验没有显著提升怎么办？
不修改结论迎合设计。分析图解析误差、动态 trace 覆盖、任务规模和 selector 公式；报告图在结构合法性或解释性上是否仍有收益。若任务中 Package 组件耦合弱，图没有效果本身也是合理结论，应简化主算法而不是继续堆复杂度。
14. 为什么项目定位为离线优化，而不是在线无限自进化？
在线自动采用更新涉及数据漂移、密钥与隐私、回滚、安全、用户影响和不可重复模型行为。离线候选搜索、held-out gate 和显式 adopt 才适合第一版开源研究系统。未来可以接入生产日志，但仍应默认 staging，而不是无条件替换。
15. 这个项目的算法贡献与工程贡献分别是什么？
算法贡献是多保真证据调度、Package Graph 上的失败信用分配、图引导有界 mutation、依赖闭合 merge 与验证门控的 GEPA 混合搜索；工程贡献是独立 Python Core、EvidenceProvider 协议、任务级 Eval、候选 DAG、断点恢复和开源报告。Agent Skill 只是薄编排适配层，不承载算法状态。
16. 如何控制 API 成本？
候选和任务结果缓存；E0/E1 在前筛选，只有晋级候选执行 E2/E3；记录高保真 work item、token、时延和可选 API 成本；Agent-native 使用宿主 Agent 能力而不要求额外 API，headless 模式再设置 API cost ceiling。
17. 为什么需要 no-skill baseline？
原 Skill 可能本身造成负迁移。只比较优化前后无法知道优化版本是否真正优于不使用 Skill。no-skill、seed skill、optimized skill 三者同时存在，才能区分恢复损害、真实增益和模型自身能力。
18. 最终如何证明“真实可用”？
至少三个非 toy Skill、公开任务与 fixtures、真实 Agent 与 API Rollout、严格 train/validation/test、多个基线、多个优化种子、成本统计、置信区间、可部署 Package、完整失败记录和外部用户可复现命令。没有这些，只能称为可运行 Demo。

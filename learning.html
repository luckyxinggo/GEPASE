02

先建立算法地图

不同工作解决的是闭环中的不同问题，不能把它们简单拼成模块名。

Search

GEPA

负责多候选搜索、任务级多样性、反思式变异、候选融合和预算控制。

Stability

SkillOpt

负责有界编辑、验证门控、拒绝编辑记忆和跨 epoch 的稳定更新。

Representation

Package Graph

负责把“改哪个文件”提升为失败归因、影响分析、闭合子图修改和安全融合。

Evaluation

skill-creator

提供 with-skill/no-skill、重复运行、assertion、盲评和成本—质量分析思想。

Evidence

SkillLens

提醒我们 Skill 存在负迁移，生成能力、消费能力和模型规模不能直接等同。

Engineering

Darwin + HL

贡献 Git ratchet、显式记忆、回归测试、失败历史和人在回路的工程方法。

一句话关系： GEPA 决定“探索哪些候选”，SkillOpt 决定“一次允许怎样改、什么情况下保留”，Package Graph 决定“失败与哪些组件有关、如何安全地改和合并”，Eval 决定“所谓提升是否可信”。
03

GEPA：项目的外层搜索骨架

Reflective evolution 的价值，在于把完整轨迹保留为可推理的学习信号。

3.1 GEPA 在优化什么？

设一个 AI 系统由若干可修改文本组件构成，候选记为 Φ。对于任务实例 x，系统执行后产生轨迹 τ、输出 y、数值评分 μ，以及自然语言或结构化反馈 μf。GEPA 的目标不是通过反向传播更新模型权重，而是在有限评测预算内寻找更好的文本候选。

Φ → rollout(x) → { trajectory τ, output y, score μ, actionable feedback μf } → reflect → Φ′

标量 reward 丢失了什么？

只知道 0 分，无法知道是触发失败、引用没读、脚本报错、输出格式错误，还是任务知识不足。

ASI 提供了什么？

错误断言、stderr、工具轨迹、实际输出、期望输出、成本、图切片等可操作信息，让 LLM 像工程师一样定位问题。

3.2 核心循环

候选选择从 frontier 采样父代
任务采样抽取反馈 minibatch
Rollout执行并收集轨迹
反思变异修改一个或多个组件
快速评测判断是否有提升
全量验证更新池与 frontier
面试易错点： GEPA 不是“随机遗传算法 + LLM”。变异不是盲目字符扰动，而是 LLM 阅读轨迹和反馈后的定向诊断；遗传性主要体现在候选继承、变异、融合与多代谱系。

3.2.1 为什么要保留 task-level feedback？

对父代 p、候选 c 和任务 i，最基本的局部信号是 Δi(c,p)=si(c)−si(p)。只保存平均分 Δ̄ 会把“修好一个困难任务、破坏另一个高风险任务”的结构抹平。GEPA 式搜索保存每个任务的输出、反馈和局部优势，父代选择和反思模型才能知道候选究竟擅长什么。

local advantage Δᵢ(c,p) = scoreᵢ(c) − scoreᵢ(p)　　|　　mean delta Δ̄ = (1 / n) Σᵢ Δᵢ

搜索信号

用 task-level 局部优势保留专长候选，避免最高平均分候选垄断全部父代机会。

反思信号

向 Reflection 提供失败任务的 assertion、grader、comparator、trace 和 graph target，而不是只给“0.73”。

接受信号

train 的严格改善只授予 validation 资格；deployable 仍由冻结 held-out Gate 决定。

3.3 Per-key Pareto Frontier 到底是什么？

当前 GEPA 为每个 frontier key 记录 best-in-class 候选。key 可以是验证样本、显式目标，或者两者组合。候选在多少个 key 上处于最佳，会影响它被选作父代的概率。

候选任务 T1任务 T2任务 T3任务 T4解释
P01.00.20.40.3T1 专家
P10.71.00.50.4T2 专家
P20.40.61.00.9T3/T4 专家
P30.80.80.80.8平均很好，但没有任何 key 第一

在 per-key frontier 下，P0、P1、P2 会被保留，因为它们至少在一个任务上最好；P3 可能落选。可是从严格多目标优化看，P3 未必被任何候选完全支配。因此：

  • instance frontier：每个验证任务一个 key，适合大量任务。
  • objective frontier：每个 accuracy、cost、latency 等目标一个 key。
  • hybrid frontier：同时考虑任务和目标，GEPASE 的初始主设置。
  • true non-dominated selector：保留全部非支配候选，可加入 crowding distance 避免候选坍缩。

3.3.1 Pareto 支配与 GEPASE 的严格接受不是一回事

若候选 a 在所有目标上不差于 b，并至少一个目标严格更好，则 a 支配 b。Pareto pool 解决的是“哪些候选值得继续探索”；Validation Gate 解决的是“哪个候选可以部署”。一个候选可以在 pool 中有局部价值，但只要 held-out 保护目标越界，就不能进入 deployable frontier。

a ≻ b ⇔ (∀j, fⱼ(a) ≥ fⱼ(b)) ∧ (∃k, fₖ(a) > fₖ(b))
deployable ⇔ (∃ primary Δ > ε) ∧ (∀ protected objective, Δ ≥ registered floor)

3.4 反思式变异

当前候选组件、任务 Prompt、Agent 输出、工具轨迹、分数、断言、stderr、成功样本中应该保留的行为，以及同类 rejected patches。
优化模型判断失败是知识缺失、路由错误、脚本缺陷、触发错误、格式不明确还是过度约束，并定位应修改的最小组件。
原始 GEPA 通常输出更新后的文本组件；GEPASE 将其约束为带证据、前置条件和预算的 PackagePatch。

3.5 系统感知融合与 DAG

如果父代 A 擅长任务集合 SA，父代 B 擅长 SB，融合希望组合互补组件。由于一个新候选可能有多个父节点，候选谱系天然是 DAG，而不是严格的树。对 Package 来说，直接按文件替换有风险：复制脚本时可能遗漏引用它的说明、测试和依赖。因此 GEPASE 融合的是依赖闭合子图。

父代 A触发与说明更好
父代 B脚本与错误处理更好
闭合子图融合检查接口与依赖冲突
子代 C重新通过全部 Gate

3.6 GEPA 在当前 GEPASE 中的真实边界

项目锁定 gepa==0.1.4，但没有让 GEPA 直接读写 Skill 目录。Core 先把 PackageCandidate 投影为稳定 component map，再由 GEPASEAdapter 规划 candidate-only WorkItem、回收 TaskScoreVector，并把 task-level score/feedback 映射到 GEPA 的候选选择骨架。文件落盘、Patch、Graph、Gate 和 deployable frontier 都仍由 GEPASE 拥有。

Python · 当前 Core 的角色分工（简化示意）
from pathlib import Path
from gepase.optimizer.candidate import build_seed_candidate
from gepase.optimizer.gepa_adapter import GEPASEAdapter

root = Path(".")
seed = build_seed_candidate(
    root,
    "benchmarks/canaries/slack-gif-creator/package",
    run_id="my-run",
)

adapter = GEPASEAdapter(
    project_root=root,
    manifest=Path("path/to/frozen-eval-manifest.json"),
    eval_run_dir=Path("artifacts/local/my-run/evals"),
)

# Adapter 只规划 typed work；Agent Host 在独立上下文执行。
work_items = adapter.plan_evaluations(
    batch=train_cases,
    candidate=seed,
    split="train",
    tier=EvidenceTier.E2_DELEGATED,
    candidate_ref="candidates/seed",
    host="agent-native", model="pinned-model", seed=42,
)

# Evidence 回收后再由 Core 评分、选择、Patch 与 Gate。
evaluation = adapter.ingest_evidence(
    seed, train_cases, split="train",
    requested_tier=EvidenceTier.E2_DELEGATED,
)

这段代码用于理解边界，不是完整优化的一键脚本。真实运行还需要 EvalPlan onboarding、隔离的 Agent submissions、PackagePatch、Gate 和 checkpoint/resume；具体参数以仓库当前 CLI 与 schema 为准。

SkillOpt：让更新过程稳定下来

GEPA 擅长多样性搜索，SkillOpt 强调训练纪律与验证门控。

4.2 为什么 full rewrite 容易退化？

归因困难

一次改十处，分数变化无法归因，也无法学习哪些编辑真正有效。

灾难性遗忘

修复新失败时覆盖已经有效的规则、格式或工具使用习惯。

局部过拟合

把 minibatch 的具体实体、路径或答案写进 Skill，validation 立即暴露。

05

SkillLens：Skill 有用，不代表总是有用

模型生成 Skill 的效用需要在完整生命周期中验证。

负迁移

Skill 可能把 Agent 约束到错误流程、引入过时知识、造成过度工具调用，最终比 no-skill 更差。

Producer ≠ Consumer

一个模型很会从经验提炼 Skill，不代表它最会使用 Skill；模型规模和 baseline 强弱也不能直接预测收益。

在 GEPASE 里的落地

  • 任何效果结论都包含 no-skill、seed skill 和 optimized skill。
  • 单独报告 negative transfer rate，而不是让平均分掩盖退化类别。
  • 在预算允许时做 cross-model 或 cross-harness transfer。
  • 结构 rubric 只作为 gate 和诊断，不能替代真实任务 utility。
  • 记录优化模型、目标模型和 Judge 模型三个角色，防止概念混淆。
06

Anthropic skill-creator：Eval 基础设施

它最值得学习的不是写作模板，而是比较与分析工作流。

渐进披露

metadata 始终可见；SKILL.md 在触发后进入上下文；references、scripts 和 assets 按需读取或执行。

Benchmark

同一 Prompt 运行 with-skill 和 baseline，多次重复，统计 pass rate、duration、tokens 及方差。

Blind comparison

比较器不知道 A/B 哪个是新版本，降低“新版本应该更好”的期待偏差。

Analyzer

识别永远通过的无区分度 assertion、高方差 case，以及效果提升与成本增长的权衡。

GEPASE 必须对 assertion 做“反例测试”：把明显错误的输出喂给断言，如果仍能通过，说明评测本身正在被优化器钻漏洞。

10

GEPASE：算法如何拼成闭环

外层负责探索，内层负责稳定，图负责结构信用分配，Eval 负责真相。

10.1 一轮完整优化

  1. 从 hybrid Pareto pool 选择父代 PackageCandidate。
  2. 采样一组失败、退化或高不确定性的训练任务。
  3. 复用同一环境、模型、EvalPlan 与 scoring policy 下已经封存的 no-skill/original 参考证据，只为新候选执行 E2 真实 Agent 任务。
  4. 对 E2 原生产物执行 E3 确定性断言，并把 observed trace 与静态 Package Graph 合并为 failure subgraph。
  5. GraphGuidedSelector 在编辑预算内选择 mutation scope。
  6. LLM 读取相关候选片段、ASI、成功行为和 rejected history，提出 PackagePatch。
  7. Patch Engine 在临时 snapshot 应用 Patch。
  8. Gate 0/1 运行 schema、precondition、引用、语法、测试与安全检查。
  9. Gate 2 在 train paired evidence 上要求至少一个预注册主目标严格改善，完全等分不能入池。
  10. Gate 3 在冻结 held-out validation 上重新执行；均值改善但类别/风险 floor 越界也必须拒绝。
  11. Gate 4 才将合格候选加入 deployable frontier。
  12. 更新 per-task / per-objective frontier、候选 DAG、成本和负反馈记忆。

E1 的当前定位：E1 仍作为“仅推演计划”的可选低保真证据保留，但 v0.1 默认关闭；它不能冒充真实执行，也不能支持候选接受。功能结论必须来自 E2 原生产物与 E3 内容级断言。

10.2 候选接受伪代码

Python · 概念性伪代码
def should_accept(parent, proposal, frozen_reference):
    candidate = patch_engine.apply(parent, proposal.patch)

    # Gate 0/1：schema、precondition、结构、测试与安全
    hard = validators.run_gate_0_and_1(candidate)
    if not hard.passed:
        rejected_store.add(proposal, reason=hard.reasons)
        return False

    # Gate 2：真实 E2 + 原生产物 E3；可复用冻结的 reference evidence
    train = paired_e2_e3(candidate, frozen_reference, split="train")
    if not train.has_strict_primary_improvement(epsilon=0.005):
        rejected_store.add(proposal, reason=train.failure_reason)
        return False

    # Gate 3：冻结 held-out validation，保护类别与高风险任务
    validation = paired_e2_e3(candidate, frozen_reference, split="validation")
    if validation.breaks_any_floor:
        rejected_store.add(proposal, reason=validation.floor_violations)
        return False

    # Gate 4：只有 held-out 严格改善才进入 deployable frontier
    return validation.strictly_improves_primary() and frontier.admit(candidate)

10.3 为什么它不是简单套壳？

  • GEPA 不原生理解 Skill Package 的文件语义、依赖闭包和脚本副作用。
  • SkillOpt 不负责多父代 Pareto 探索，也不联合训练完整目录。
  • Package Graph 不只是报告，它改变 component selection、edit budget、validation intensity 和 merge。
  • 独立 Python Core 管理 Evidence、候选、图、Pareto 与 Gate；Agent Orchestrator Skill 只负责领取任务、委派子智能体和回写结果。
  • Eval Core 把 E0 静态、可选 E1 推演、E2 真实执行和 E3 可执行断言统一到 typed schema，同时禁止 planned/observed 混淆。
  • 图必须实际参与 selector、impact closure、merge 和 Gate；v0.1 不把“图优于随机”的消融当作收尾条件，也不做未经实验的优越性宣称。

10.4 设计概念落到哪些代码？

src/gepase/package/Package snapshot、异构 IR、静态/动态图、failure slice 与 graph diff。
src/gepase/evals/WorkItem、Submission、E0–E3、TaskScoreVector、paired evidence 与统计。
src/gepase/optimizer/GEPA adapter、候选池、graph selector、Gate、evolution 与同包多父融合。
src/gepase/mutation/typed PackagePatch、提案、原子应用/回滚与影响分析。
src/gepase/store/artifact、candidate、checkpoint、evolution pool 与 rejected-edit memory。
.agents/skills/gepase-orchestrator/薄 Agent Host 适配层；不拥有分数、候选或接受状态。

Package Graph：什么时候真正有用？

图是结构化中间表示，重点是可解释的 slicing、closure 和 impact analysis。

11.1 节点与边

节点

frontmatter 字段、SKILL 章节、instruction block、reference chunk、script module/function、asset、eval case、output artifact。

边

contains、references、imports、calls、declares、produces、reads、executes、covers、fails_at、contributes_to。

11.2 失败切片示例

Eval E17 失败空行解析 assertion
parse_rows()动态 executes + stack frame
脚本调用说明SKILL.md references
无关领域文档未访问，不进入 scope

从失败 assertion 反向沿 produces、calls、references、executes 等边扩展，得到最小相关子图。LLM 只看到相关函数、调用说明、对应测试和必要邻居，而不是整个 Package。这同时降低上下文成本和无关修改概率。

11.3 Graph-guided selector

score(v) = 3.0·coverage + 2.0·inverse_distance + 1.4·access + 1.2·severity + 0.8·yield + 0.6·explore − 1.0·fan_out − 1.5·regression

当前实现先从 failure/evidence 节点沿允许的边做 BFS，再为可编辑节点计算透明的加权和。距离项使用 1 / (1 + d)； 动态访问、诊断严重度、历史成功率和探索奖励提供正向信号，公共节点的 fan-out 风险与历史回归提供惩罚。

特征权重直觉
failure_coverage+3.0一个节点能解释多少当前失败，是最强正向信号。
inverse_distance+2.0离失败证据越近，越可能是局部根因。
dynamic_access / severity+1.4 / +1.2真实执行访问与高严重度诊断提高优先级。
historical_yield / exploration+0.8 / +0.6兼顾历史有效区域和未充分探索区域。
fan_out / regression−1.0 / −1.5依赖面大或曾引入回归的节点更保守。
这是可检查、可替换的工程启发式，不是已经证明最优的图算法。v0.1 的证据只支持“图已经进入定位、作用域和验证决策”； 如果未来要声称 graph-guided 优于 random、round-robin 或 trace-only，再补等预算消融。
为什么第一版不用 GNN？ 单个 Skill Package 图规模小，监督样本也少。GNN 会增加训练数据需求和解释成本，却未必优于透明规则。只有积累大量跨 Skill 的 graph—patch—outcome 数据后，学习式 selector 才合理。

12

Eval 与统计：项目可信度的核心

优化器可以很朴素，评测不能含糊。

12.1 E0–E3 不是四套分数，而是四种证据保真度

Tier回答的问题当前用途不能证明
E0Package 能否解析？schema、引用、语法和安全规则是否通过？廉价结构 Gate；所有候选先过。Agent 能完成真实任务。
E1如果执行，计划可能如何展开？可选低保真诊断；v0.1 默认关闭。真实工具调用、产物正确或候选可接受。
E2隔离 Agent 是否真正完成了用户任务？保存 task-native outputs、transcript、trace、usage、timing 与 hashes。产物内容一定满足隐藏要求。
E3对 E2 原生产物运行内容级 assertion 后是否满足可执行契约？与独立 grader、comparator 一起构成功能证据。单一断言通过就等于综合质量 1.0。

12.2 为什么角色必须隔离？

Executor只看用户任务、fixture 和 candidate ref，实际完成任务。
Deterministic Grader读取原生产物，运行内容级 assertion。
Independent Grader核验正确性、完整性、专业度与可用性。
Comparator匿名比较 A/B，不知道候选身份与预期胜者。
Analyzer / ASI解释失败，并把证据定位到可编辑 Package 节点。

Executor 看不到 assertion、rubric、expected answer、sibling output 或 candidate identity；不同角色不共享聊天上下文，只通过 typed submission 交换证据。 这样可以降低“执行者顺手给自己打分”和 sibling leakage。相同环境、模型、EvalPlan、scoring policy 与 reference Package hash 下，no-skill/original 证据可以安全缓存，新候选只需重跑自己的分支。

12.3 Train 与 frozen Validation

Train

允许进入反思上下文，用于失败归因、Patch 提案和 Gate 2。严格改善才有资格进入 held-out。

Frozen Validation

在 EvalPlan 审核后冻结；不向 proposer 泄露正确答案，用于 Gate 3 与最终 deployable 判定。

独立 test split、多 seed 与跨模型复验适合更强泛化结论，但不是应用框架 v0.1 的强制收尾条件。当前公开 canary 使用 5 个 train 与 3 个 frozen validation case，并明确限制结论范围。

12.4 TaskScoreVector：保留多目标语义

维度回答的问题典型证据
task_correctness任务的核心事实与行为是否正确？断言、task-native artifacts、事实核验。
output_quality产物是否完整、专业、可用、符合格式？独立 grader 与盲 Comparator。
skill_gain相对 no-skill，Skill 是帮助还是伤害？同轮 paired comparison。
reliability执行是否稳定，是否有超时、缺失或工具错误？typed failure、重复执行与提交完整性。
efficiency是否以合理上下文、工具调用与时延完成？usage、timing、trace；不要求框架代管 API 账单。
package_quality修改后 Package 是否结构健康、可维护、可执行？E0、graph diagnostics、tests 与 safety Gate。

Trigger Eval 的 precision、recall、F1、accuracy 与 trigger rate 单独报告，不混入 Functional Eval；否则一个 description 写得很会触发，就可能掩盖执行结果很差。

12.5 当前统计与接受规则

  • 同一任务、同一环境、同一模型配置的 paired before/after。
  • 至少一个预注册主目标严格改善；默认 epsilon 为 0.005，完全等分拒绝或记为 inconclusive。
  • held-out 同时检查均值、逐 case 胜负、类别 floor 与高风险 floor；保护目标优先于总均值。
  • paired bootstrap 95% CI 描述不确定性；当前 accepted candidate 的区间为 [0.08928, 0.17106]。
  • 记录 Agent work、usage、timing、cache provenance 与 artifact hashes；墙钟时间是工程约束，不是 Skill 质量分数。
  • 失败候选和不显著结果也进入公开 artifact。

12.6 这个应用框架怎样才算成功？

v0.1 的目标不是完成论文式全量消融，而是把一条真实闭环做可信：对一个非 toy、可本地执行的公开 Skill，框架能从真实 Agent 失败中产生有界 PackagePatch， 并在冻结 held-out 上得到可量化严格改善，同时输出可审计证据、失败候选、可部署 Package 与清晰报告。更广泛的 Skill、模型、seed 与 selector 比较属于后续外部有效性，而不是把首个有效结果无限推迟的前置条件。

13

面试思考问答

回答要围绕问题定义、设计取舍、实验依据和局限，不要堆术语。

1. Skill 优化和 Prompt 优化有什么本质区别？
Skill 的核心仍包含上下文文本，所以与 Prompt 优化同源；区别在于 Skill 是可复用、可触发、可包含脚本和资源的程序化 Package。优化对象不只是指令措辞，还包括加载路由、工具策略、参考知识、可执行代码和依赖一致性，因此更接近外部可训练 Agent policy。
2. 为什么以 GEPA 为主体，而不是直接使用 SkillOpt？
SkillOpt 对单文档的局部稳定更新很强，但 GEPASE 还需要保留在不同任务上具有互补优势的多个候选，并进行多父代融合。GEPA 的候选池、per-key frontier、反思变异和 merge 更适合作为外层搜索；SkillOpt 的有界编辑和 validation gate 用于增强其稳定性。
3. GEPA 为什么可能比只优化最高平均分候选更好？
平均分会掩盖专长。某候选可能只修好了少数困难类别，平均提升不大，但这些局部能力可以在后续融合或继续变异中转化为更强系统。per-key frontier 为这些候选保留进化机会，减少贪心搜索过早收敛。
4. GEPA 的 Pareto 是严格的非支配前沿吗？
默认不完全是。官方 GEPA 的 per-key frontier 重点保留在某个样本或目标上 best-in-class 的候选；一个各方面都不错但从未单项第一的候选可能被遗漏。GEPASE 保留 task/objective 局部优势与 Pareto 候选池，但把“搜索中值得继续探索”和“可以部署”分开：后者仍必须通过严格 held-out Gate。
5. 图算法为什么不是为了包装项目？
图直接影响四个决策：失败相关组件选择、Patch 的依赖闭包、公共接口修改的验证强度、多个父代的同包子图融合。如果移除图只影响可视化，它就是装饰。v0.1 已验证图进入这些代码路径，但不声称它优于 random 或 trace-only；只有未来要做这种优越性主张时，才需要等预算消融。
6. 为什么不用 GNN？
单包图小、跨 Skill 标注数据少，透明启发式更便于调试与归因。GNN 只有在积累足够多 graph—patch—outcome 历史后才可能优于手工 selector。第一版引入 GNN 会增加复杂度但缺乏可信训练信号。
7. 如何防止 LLM 通过修改 Skill 钻 Eval 漏洞？
严格隔离 frozen validation；对 assertion 做反例和 mutation testing；不把 assertion、rubric 或预期答案提供给 Executor/Proposer；监控候选是否写入任务实体；使用分组切分与泄漏检查；保留独立 Grader、匿名 Comparator 和人工抽查。未来若增加 test，它必须在优化冻结后一次性使用。
8. 为什么不能只用 LLM-as-a-Judge？
Judge 会受措辞、长度、顺序和自我偏好影响，还可能与 proposer 共享模型偏差。可执行任务应优先使用脚本、文件和 assertion 验证；Judge 仅评价难以程序化的质量，并尽量盲化候选身份、使用独立上下文和校准样例。
9. 有界 Patch 如何对应 SkillOpt 的 textual learning rate？
学习率不再是连续数值，而是一次允许的操作数、修改文件数、增删文件数、替换字符数，以及是否允许脚本/拓扑编辑。高风险或高 fan-out 节点应使用更小预算并提高验证强度；Patch 的 precondition hash 还能阻止基于过期节点盲改。
10. 如何衡量图引导带来的样本效率？
如果未来要回答这个研究问题，应在相同 target/optimizer 模型、任务、proposal 次数和 metric-call 预算下，比较达到相同 validation score 所需调用数、accepted-improvement yield、无效 Patch 比例与回归率。不能只比较墙钟时间，因为并发配置可能不同；这不是 v0.1 应用闭环的完成 Gate。
11. 如何避免灾难性遗忘？
把历史能力固化为 regression tasks 和 golden traces；使用小步编辑；完整 validation 检查旧类别；对公共节点提高验证覆盖；记录 rejected edits；定期提出 compression 而不是只追加规则。它不能保证零遗忘，但能将遗忘变成可检测和可回滚的问题。
12. Package merge 最大的技术风险是什么？
组件之间存在隐式接口。只复制一个脚本可能遗漏调用说明、依赖和测试；只复制文档可能引用不存在的文件。GEPASE 因此融合依赖闭合子图，先做静态冲突检测，再对冲突部分生成结构化 resolution patch，最后重新通过全部 Gate。
13. 如果图引导实验没有显著提升怎么办？
不修改结论迎合设计。如果开展消融，应分析图解析误差、动态 trace 覆盖、任务规模和 selector 公式；如果图只提供可解释定位或结构安全，就只报告这部分价值。若长期既不改变决策也不改善工程质量，再简化设计，而不是为了“看起来像算法”继续堆复杂度。
14. 为什么项目定位为离线优化，而不是在线无限自进化？
在线自动采用更新涉及数据漂移、密钥与隐私、回滚、安全、用户影响和不可重复模型行为。离线候选搜索、held-out Gate 和显式 deploy 才适合第一版开源应用框架。未来可以接入生产日志，但仍应默认 staging，而不是无条件替换。
15. 这个项目的算法贡献与工程贡献分别是什么？
更准确的表述是“系统性组合创新”：以官方 GEPA 搜索骨架为主体，把 Package Graph 上的失败信用分配、图引导有界 mutation、依赖闭合同包 merge 和严格 held-out Gate 组合到完整 Skill Package；工程上提供独立 Python Core、typed evidence、候选 DAG、断点恢复和开源报告。v0.1 已证明闭环在单 canary 上有效，但不把每个部件都包装成已独立验证的新算法。
16. 如何控制 API 成本？
默认 Agent-native，避免强制额外 API key；在环境、模型、EvalPlan、scoring policy 和 hash 全等时复用封存的 no-skill/original 参考证据；同阶段独立角色并行但保持上下文隔离；失败尽早经过结构 Gate。Core 记录调用、估算 token 与时延，但 v0.1 不建设 API 费用或人民币账单系统。
17. 为什么需要 no-skill baseline？
原 Skill 可能本身造成负迁移。只比较优化前后无法知道优化版本是否真正优于不使用 Skill。no-skill、seed skill、optimized skill 三者同时存在，才能区分恢复损害、真实增益和模型自身能力。
18. 最终如何证明“真实可用”？
应用框架的第一道标准是：一个非 toy 公开 Skill 经真实 Agent paired eval 后，在冻结 held-out 上出现严格可量化提升，并能从原始证据复算、解释、回滚和导出。GEPASE v0.1 已达到这一标准：+0.12427、3/3 held-out wins、一个 deployable Package；同时明确它只是单 Skill、单模型快照、单次搜索证据。跨 Skill、seed 和模型复验会提高外部有效性，但不应把已经完成的真实闭环贬成 toy demo。
19. 为什么原始 Skill 可能比 no-skill 更差？
Skill 会改变 Agent 的注意力、流程约束、工具选择和输出偏好。如果规则过强、验收不足或参考资料过时，它可能造成负迁移。R3 的 original 平均 skill_gain 为 −0.0455，正说明“Skill 可执行”不等于“Skill 有增益”；因此 no-skill baseline 必须与 original 同轮隔离运行。
20. 多父 Merge 是不是合并不同 Skill？
不是。父代必须来自同一个 base Package、同一 frozen EvalPlan 和兼容 lineage；合并的是同一 Skill 内不同候选的互补改动，并补齐依赖闭包、检查冲突后重新过完整 Gate。跨 Skill Package merge 被明确禁止。v0.1 的 merge child 总均值为正仍因 emoji_animation 类别回归被拒绝，说明 merge 也没有特殊通行证。
